NTLMancer

Transforme un relais NTLM-vers-HTTP réussi en session navigateur authentifiée. Au lieu d'extraire des identifiants, NTLMancer garde vivant le socket TCP authentifié et route le trafic du navigateur à travers une passerelle SOCKS locale, ce qui maintient l'identité active et de courte durée.

1. Objectif

Un relais NTLM classique consomme l'authentification pour exécuter une action unique côté cible. NTLMancer part de la même primitive mais change le résultat : au lieu de brûler l'authentification, il garde le socket TCP authentifié ouvert, puis expose cette connexion vivante comme une session navigable. L'opérateur parcourt alors l'application cible avec l'identité relayée, comme s'il était la victime, sans jamais posséder ses identifiants.

Le trafic du navigateur passe par une passerelle SOCKS4/4a/5 locale. Chaque requête sortante est associée à l'identité capturée correspondante, puis rejouée sur le socket authentifié. La session reste courte par nature : dès que la connexion NTLM meurt ou devient ambiguë, le binding est retiré et il faut une nouvelle capture.

2. Architecture

Tout le design tourne autour de trois principes de sûreté qui protègent l'intégrité du canal authentifié :

  • Pas de remplacement silencieux : un socket lié n'est jamais remplacé en douce par une nouvelle connexion non authentifiée.
  • Un seul worker : exactement un worker peut lire ou écrire sur ce socket, ce qui interdit la désynchronisation de protocole.
  • Retrait sur incertitude : un framing ambigu, une perte d'authentification ou une I/O incertaine retire immédiatement le binding.

Le flux de binding fait passer l'authentification capturée par un adaptateur de capture vers un socket HTTP lié, possédé par un unique worker FIFO. Les requêtes du navigateur arrivent par SOCKS et sont ordonnancées vers cette session authentifiée, une à la fois par identité. 

Capture NTLM (relais réussi)
    -> adaptateur de capture
    -> socket HTTP lié + authentifié
    -> worker FIFO unique (1 par socket)
    -> file d'attente par identité
Navigateur -> SOCKS4/4a/5 (127.0.0.1:1080)
    -> sélection d'identité
    -> rejoue la requête sur le socket lié

Le parsing HTTP/1.1 s'appuie sur h11 pour une lecture incrémentale et stricte. Les protections anti-framing rejettent les requêtes ambiguës plutôt que de risquer une désynchronisation qui corromprait l'état du socket partagé.

3. Workflow

Python 3.10+ est requis. Le lanceur crée automatiquement un environnement virtuel et installe les dépendances à la première exécution. On lance NTLMancer contre une cible, puis on configure le navigateur avec un proxy SOCKS5 sur 127.0.0.1:1080. 

# Opération de base
./ntlmancer -t https://vault.lab.local/

# Accepter plusieurs captures successives
./ntlmancer -t https://vault.lab.local/ --keep-relaying

# Plusieurs cibles avec surveillance de fichier
./ntlmancer --targets-file targets.txt --watch

# Ajuster les listeners de capture
./ntlmancer -t http://app.lab.local/ \
  --http-port 8080,8082-8084 \
  --no-wcf-server \
  --no-raw-server

Les timeouts et limites sont explicites et bornent chaque étape du canal : taille de file par identité (--http-queue-size, défaut 32), premier octet (--http-first-byte-timeout), corps, réponse, en-têtes, plus des plafonds sur les tailles d'en-tête et de corps. Ces bornes évitent qu'une requête lente bloque le worker unique ou corrompe le framing.

4. IIS kernel-mode

IIS peut terminer l'authentification en kernel-mode, ce qui change la façon dont les routes réagissent aux requêtes mutantes. NTLMancer gère ce cas avec une classification de routes : on déclare les chemins protégés qui reçoivent des requêtes modifiantes, et l'outil route en conséquence. 

./ntlmancer -t https://portal.lab.local/ \
  --kernel-auth \
  --protected-route /api \
  --protected-route /admin

Des sondes keepalive optionnelles (--keepalive-path, --keepalive-interval) maintiennent la connexion vivante entre deux actions de l'opérateur, ce qui allonge la fenêtre exploitable sans réauthentification.

5. Politique de trafic

Un navigateur émet beaucoup de requêtes vers des destinations tierces. NTLMancer contrôle ce que la passerelle laisse passer directement via trois modes de politique :

  • deny (défaut) : rejette toute destination non liée.
  • allowlist : autorise des hôtes et suffixes de domaine configurés.
  • all : laisse passer n'importe quelle destination.
./ntlmancer -t https://portal.lab.local/ \
  --passthrough allowlist \
  --allow-host static.portal.lab.local \
  --allow-domain-suffix .assets.lab.local

6. Console et API

La console interactive de binding expose des commandes de suivi de session : sessions affiche transport, destination, identité, état du worker, âge et nombre de requêtes ; targets liste les destinations connues ; status résume les listeners et les bindings actifs ; quit ou exit lancent un arrêt contrôlé. La sortie se fait aussi par Ctrl-D, Ctrl-C ou SIGTERM.

Une API de contrôle locale, en loopback uniquement (--api-address, défaut 127.0.0.1:9090), permet le monitoring programmatique : 

GET /health
GET /v1/sessions
GET /v1/sessions/details

7. Limites

  • HTTP/1.1 est le seul protocole applicatif supporté. Les upgrades WebSocket et les réponses en streaming indéfini sont rejetés pour préserver l'état du socket.
  • Extended Protection, channel binding et exigences de signing peuvent empêcher le relais en amont.
  • Une connexion NTLM ne peut pas être reconstruite après expiration : il faut une nouvelle capture d'authentification.
  • L'outil suppose un relais déjà réussi. Il ne fournit pas la primitive de coercition ni le downgrade ; il capitalise sur l'authentification une fois relayée.

8. Ce que cela démontre

NTLMancer déplace la valeur d'un relais NTLM : d'une action unique vers une session interactive. Le projet force à comprendre finement le cycle de vie d'une connexion NTLM authentifiée, le framing HTTP/1.1, la gestion de la concurrence autour d'un socket partagé et le comportement particulier de l'authentification kernel-mode d'IIS.

Côté engineering, il combine parsing HTTP incrémental strict, ownership à worker unique, ordonnancement FIFO par identité, passerelle SOCKS multi-version, politique de trafic configurable, console interactive et API de contrôle en loopback. Les trois règles de sûreté ne sont pas décoratives : elles cadrent chaque décision de conception pour éviter la désynchronisation de protocole et la fuite involontaire de session.
