The problem

An NTDS.dit holds most of the static state of an Active Directory domain: users, groups, machines, the hierarchy, memberships, delegation, GPOs, trusts, security descriptors, and AD CS objects. The problem is that none of it is stored the way BloodHound expects. ntds2bh reads the ESE database, rebuilds the schema and the identities, resolves the relations, interprets the ACLs, and writes the BloodHound CE v6 collections. The whole run is offline; no LDAP query touches the domain.

In pentest work the first thing people associate with NTDS.dit is credential extraction. The database also carries the shape of the domain: the objects, their attributes, and most of the relations that explain who belongs to what and who can act on what. That graph is what BloodHound makes readable, and when live access to the domain controller is gone or unwanted, the file still contains it. The layer that turns the internal records into BloodHound objects and edges is what I built.

Where ntds2bh sits

The project sits between an NTDS parser and a BloodHound collector. That placement matters, because it keeps me from describing the tool as a replacement for things that do a different job.

Tool or layer What it does well What it does not cover here
SharpHound Collects BloodHound data directly from the environment. Needs live collection and depends on connectivity and the collector's rights.
ntdissector Low-level reading and normalization of NTDS.dit. Does not on its own rebuild the full BloodHound graph.
ntds2bh Keeps the useful NTDS parsing and adds the BloodHound reconstruction. Cannot see the purely live data that is absent from the snapshot.

The low-level parsing in ntds2bh is adapted from ntdissector, which builds on dissect-database. The work specific to this project starts where the NTDS records have to become stable identities and then consistent BloodHound relations.

What NTDS.dit actually stores

NTDS.dit uses the Extensible Storage Engine (ESE), historically JET Blue, a database engine built into Windows. It stores data as pages, tables, indexes, and records, with its own internal representation. Reading the database is only the first step. A datatable row does not arrive as a tidy dictionary with objectSid, memberOf, and distinguishedName. Attribute names come through the schema, some names have to be rebuilt, relations live in a separate table, and security descriptors can be referenced by id instead of stored inline.

Structure Useful content Why it matters
datatable Active Directory objects and most of their attributes. Basis for rebuilding users, groups, computers, OUs, GPOs, domains, and AD CS objects.
link_table Linked relations between objects. Lets memberships be rebuilt from links rather than a text field.
sd_table Binary security descriptors. Needed for ACLs and for attributes that point at a descriptor by id.

The internal columns use attribute identifiers and representations that do not mean much to the rest of the pipeline, so the first phase builds a view of the schema: LDAP names, object classes, property GUIDs, and the information needed to read ACEs. That schema dependency is what makes the ACL work possible. An ACE can target a property GUID or a class GUID, and until those GUIDs are tied to their meaning, there is no clean way to decide whether a permission should become AddMember, WriteSPN, WriteAccountRestrictions, or no edge at all.

Identities before relations

The graph becomes useless the moment one object gets two different identities. Before creating any relation, ntds2bh builds the indexes that map an internal representation to a stable BloodHound one.

The Distinguished Name is not stored as a full string on each record. Reconstruction uses the Distinguished Name Tag (DNT), the parent DNT, the Relative Distinguished Name, and the schema, walking up the internal hierarchy until it reaches the domain root.

This resolution happens before any edge is emitted. Otherwise a group membership could be created against a temporary identifier and then fail to line up with the final object. The pipeline keeps several indexes for this: SID to object, DN to object, GUID to object, SPN to account, and DNT to record.

The object type matters as much as the identifier. Two objects with similar attributes do not always belong in the same collection, so routing looks at the Active Directory class and, when needed, at sAMAccountType. Service accounts are the clearest example. A Group Managed Service Account (gMSA) is modeled as a user, while a Delegated Managed Service Account (dMSA) follows the computer path. Routing on sAMAccountType alone, or on a loose test, produces typing errors quickly, so the class drives the decision.

Rebuilding relations

Once identities are stable, the pipeline reconnects the objects. Group memberships come from link_table. A link entry gives internal references, not a BloodHound PrincipalSID, so the processing has to find the member and the group from their references, resolve their final SID or identifier, decide the member's BloodHound type, confirm the link is still active, and emit the relation once.

The active-link check exists because of a concrete bug. A relation deleted in Active Directory can still be physically present in link_table. If link_deltime and link_deactivetime are ignored, an old membership comes back into the graph even though it no longer exists logically. ntds2bh filters those links in _is_deleted_link before using them.

The primary group follows a different path. It is stored on the user or computer as primaryGroupID, and the PrimaryGroupSID is rebuilt from the domain SID and that RID. It must not be injected a second time into the group's ordinary member list, or the graph ends up with two copies of the same membership. ContainedBy relations come from the DN hierarchy: after the full DN is rebuilt, the parent is found and typed as an OU, container, or domain. None of these are reliable until identity resolution has already finished.

Security descriptors to BloodHound edges

This is the part where a mistake costs the most. A mis-serialized property only breaks display. A misread ACE can invent an attack path, which is worse than missing one.

An NTDS object does not always carry its full descriptor inline. It can hold an sd_id that points into sd_table, because Active Directory deduplicates descriptors heavily and many objects share one. The parser resolves that reference, reads the owner, group SID, DACL, and ACEs, and only then starts interpreting each ACE. Interpretation is not a flat mask-to-name table. The edge depends on several dimensions at once: the access mask, the ACE type and allow or deny, the object or property GUID it targets, the class of the target object, the principal SID, and the inheritance flags.

The clearest way to see why a table is not enough is the write-property case. The same DS_WRITE_PROP bit becomes a different edge depending on what it targets: 

if _has_priv(mask_val, MASKS["DS_WRITE_PROP"]):
    if _target_matches(object_type, {"group"}) and _can_write_property(
            mask_val, has_object_type, obj_type, RIGHT_GUIDS["AddMember"]):
        rights.append("AddMember")

    if _target_matches(object_type, {"computer"}) and _can_write_property(
            mask_val, has_object_type, obj_type, RIGHT_GUIDS["AddAllowedToAct"]):
        rights.append("AddAllowedToAct")

Write-property on the member attribute of a group is AddMember. The same write-property right on a computer, carrying the msDS-AllowedToActOnBehalfOfOtherIdentity GUID, is AddAllowedToAct. A write-property ACE that points at some other attribute produces no edge. _can_write_property enforces that: it requires the write bit and either an ACE with no specific object type, which generalizes to GenericWrite, or an object type GUID that matches the exact property. Change the target class or the property GUID and the right changes with it.

A few well-known SIDs need their own handling. GENERIC_ALL short-circuits to GenericAll and stops. DS_CONTROL_ACCESS with the right extended-right GUID becomes GetChanges and GetChangesAll on the domain, ForceChangePassword on a user or computer, or Enroll on a certificate template. DS_SELF on the member property of a group becomes AddSelf, not AddMember. And NT AUTHORITY\SELF is dropped rather than rewritten to the object's own SID, because SharpHound emits no self-edge for it; rewriting it naively would invent an edge that the reference collector does not produce.

The last concern is a truncated or invalid descriptor. The worst outcome is turning an unparseable descriptor into a silent empty ACL, which reads as no permissions at all. The NTDS2BH_STRICT_PARSING environment variable makes those cases raise instead, so a parsing failure is loud rather than a false absence of rights.

The cases that break naive code

The interesting bugs in this project were never JSON or syntax. They were specific representation details.

gMSA membership. In the lab, msDS-GroupMSAMembership held an eight-byte value that was an sd_id, not a full security descriptor. The first version treated it as a blob and produced no ReadGMSAPassword edge. The fix recognizes the reference, resolves it in sd_table, parses the descriptor, and runs the same ACE engine: 

# the value is an sd_id reference, so resolve it before parsing
raw_obj["msDS-GroupMSAMembership"] = ntds.resolve_sd_reference(
    raw_obj.get("msDS-GroupMSAMembership"))

# then each principal in that descriptor becomes a ReadGMSAPassword edge
gmsa_aces, _ = resolve_aces_from_sd_value(record.get("msDS-GroupMSAMembership"), ...)
for ace in gmsa_aces:
    aces.append({**ace, "RightName": "ReadGMSAPassword"})

dMSA. dMSAs look enough like other service accounts that a loose router is dangerous. In the target model they follow the computer path, so the object class is used explicitly to keep them out of the gMSA and ordinary-user buckets.

GPO links. Group Policy links live in gPLink. The GUID in that string identifies the groupPolicyContainer, but the node identifier is the real objectGUID, so the two have to be reconciled. The link options are interpreted too: a disabled link must not appear active, and the enforcement bit becomes IsEnforced.

Constrained delegation. msDS-AllowedToDelegateTo holds Service Principal Names, not the target account SID, so the pipeline builds an SPN-to-object index, with a fallback on account names. RBCD uses a security descriptor; its allowed principals become AllowedToAct, which has to be kept separate from AddAllowedToAct, the right to change the RBCD configuration itself.

AD CS. AD CS objects live mostly in the configuration partition. The converter handles templates, enterprise CAs, root CAs, AIA CAs, NTAuth stores, and issuance policies. Templates need flags, periods, key usages, and policies decoded; CA certificates stored in the directory can be decoded for subject, serial, and thumbprint. Settings that exist only in the CA server's registry cannot be rebuilt from NTDS.dit alone. Trusts come from trustedDomain objects and are serialized into BloodHound's trust format.

BloodHound CE v6 output

Each collection follows the version 6 envelope: a data array and a meta block. The writer also checks that meta.count equals the number of objects actually written. 

{
  "data": [ { "...": "BloodHound object" } ],
  "meta": { "type": "users", "count": 1, "version": 6 }
}

The project emits thirteen collections: users, computers, groups, domains, ous, containers, gpos, certtemplates, enterprisecas, rootcas, aiacas, ntauthstores, and issuancepolicies. The output is either a folder of JSON or a single bloodhound.zip, imported into BloodHound CE like an ordinary collection.

Validation

Validation took about as long as parts of the development. A raw diff against SharpHound is not enough on its own: when the two outputs disagree, I still have to know which one matches the state actually stored.

I build the test environments with ADBuilder, so I can create a group, a right, a delegation, or a relation on purpose and know before the run what should appear. That is the difference that makes a verdict possible. On a domain I do not control, a missing edge could come from the converter, the reference collector, the collection account's rights, or a wrong assumption about the configuration. In a lab I built for the test, I can go back to the source ACL and decide.

Evidence comes from three places that have to agree: the configuration I created on purpose, the stored data read through LDAP, PowerShell, or NTDS inspection, and the reference collection from SharpHound on the same state.

The integrity checker does not stop at object counts. It compares relations as exact tuples per relationship field, compares the properties shared by matched objects, flags meta.count that disagrees with the array length, and reports missing or extra collections, duplicate identifiers, and dangling references. It also prints a summary of node and edge counts per side, so a parity claim can be read as the numbers the checker produced rather than a single headline figure. I keep terms like false positive and false negative for the controlled lab, where the expected state is known. For the global comparison with SharpHound I use match, present only in the reference, or present only in the candidate, so SharpHound does not become an absolute oracle.

On a campaign snapshot, over the static perimeter comparable to SharpHound DCOnly, SharpHound and ntds2bh produced the same node and edge totals that the checker reported, with aligned identifiers and types and no dangling references in that comparison. Equal comparable graph is not the same as every property being identical. After I hardened the checker, several property differences that the older comparison ignored became visible instead.

Difference Nature State
objectguid missing on some outputs Readable property, not emitted everywhere. Output gap.
isaclprotected Derivable from the security descriptor. To harmonize in serialization.
adminsdholderprotected More complex semantics. Must not be replaced naively by adminCount.
OWNER RIGHTS derived flags Derived-property semantics. Still to align fully.
DomainSID on some AD CS objects Model or serialization difference. Visible in the checker.

I prefer to leave these visible. A zero-difference number reached by excluding every awkward property would be less useful than a checker that shows what is left. The campaign also turned up the opposite case: ACEs that were genuinely present in Active Directory where the reference collection did not produce the matching edge, for example WriteAccountRestrictions on a user and AutoEnroll on a template. Looking only at the reference ZIP would have treated real data as an error, which is exactly why the method uses three sources.

At the revision behind this writeup, the unit suite runs 51 tests. 47 pass, and the 4 that fail do so only because they need binary .dit fixtures that are not shipped with the source archive; they are not logic failures. The lab comparison numbers above are from a specific campaign snapshot and are not reproducible from the repository alone, since they need a real NTDS.dit and a SharpHound collection of the same state.

Limits

The main limit is the snapshot. NTDS.dit gives a rich view of the directory, not the whole Windows environment.

  • Active sessions: they depend on the live state of the machines.
  • Local groups: not described by the NTDS database alone.
  • Service and host state: absent from the directory snapshot.
  • Registry: some settings, including AD CS server settings, live elsewhere.
  • SYSVOL: policy file contents are not in NTDS.dit.
  • Time: the graph is the domain state at the moment of the copy.

That also changes how to read the graph. A relation rebuilt from an old snapshot can be historically correct and no longer true today. ntds2bh reconstructs the static graph observable in the copy; it does not prove that a path is still exploitable in the current environment.

Running it

The minimal path is a few commands: 

uv venv
source .venv/bin/activate
uv sync

uv run ntds2bh -n ntds.dit -o bloodhound.zip

To write the collections as separate files: 

uv run ntds2bh -n ntds.dit --no-zip -o BloodHound_output

The result imports into BloodHound CE like an ordinary collection.

Attribution

The database reading does not start from scratch. Part of the ESE parsing and NTDS normalization is adapted from ntdissector, which builds on dissect-database. The work specific to ntds2bh is the part that produces the graph: resolving sd_table references, building the SID, DN, DNT, GUID, SPN, and primary-group indexes, typing objects for BloodHound, resolving ACEs into rights, rebuilding memberships, delegation, GPOs, trusts, and hierarchy, normalizing the AD CS objects, writing the BloodHound CE v6 collections, and the semantic integrity check over the output.

The question at the start was whether a copy of NTDS.dit could become a useful BloodHound graph again without talking to the domain. For most of the static graph the answer is yes, on one condition: do not treat NTDS as a file you just convert. Rebuild the identities before the relations, understand how links are stored, follow the references into the security descriptors, read each ACE correctly, and check every rule against a known state. ntds2bh does not replace SharpHound and does not claim the live state of the domain. It adds a different way to work: start from a cold artifact and recover as much of the real Active Directory structure as it actually contains.
