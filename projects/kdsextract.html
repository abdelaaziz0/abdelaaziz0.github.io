KDSExtract

Samba answered an LDAP Compare by formatting the caller's attribute name and value straight into an internal filter string. That one line lets a normal user change the comparison operator and reach attributes the server is meant to hide. KDSExtract rides it into an ordered oracle, recovers the KDS root key one byte at a time, and derives gMSA passwords from it offline.

Samba's AD DC answers an LDAP Compare request by building a small internal search filter and evaluating it. Before the 2026 security releases it built that filter by formatting the request's attribute name and value straight into a string. That construction is CVE-2026-58222, rated 8.8, and it does two things at once: it lets a caller change the comparison operator, and it runs the comparison in a context that skips the server's confidential-attribute checks. KDSExtract uses the result as an oracle to read msKds-RootKeyData, the Group Key Distribution Service (GKDI) root key, one byte at a time, then derives gMSA passwords from it offline.

The vulnerability was found and reported by others, and the gMSA key derivation is already documented in MS-GKDI and implemented in tools like GoldenGMSA. What this project adds is a tested implementation of the whole chain: the oracle, the byte recovery, a dependency-free derivation that reproduces Samba's own reference vectors, and a lab that ties a recovered key back to the controller's ground truth. This is authorized lab work against environments I control. The code shown below is from commit 80a08cc.

The bug

Samba built the Compare filter roughly like this: 

filter = talloc_asprintf(local_ctx, "(%s=%*s)", req->attribute,
                         (int)req->value.length, req->value.data);

req->attribute and req->value come from the client's CompareRequest. At the protocol level the client sends them as two octet strings, which is exactly what KDSExtract's compare() puts on the wire. Samba pastes both into the filter with no validation of the attribute name and no escaping of the value. The two problems are separate, and each is limited on its own.

An LDAP Compare is an equality test, (attribute=value). If the attribute string already ends in >, the filter reads (attribute>=value), which is a greater-or-equal match. The client controls the attribute field, so the client controls the operator. On its own that only lets you compare values you were already allowed to read.

The second problem is that this internal search runs without the marker Samba uses for untrusted requests, so the access-control module that normally hides confidential attributes does not apply. Attributes like msKds-RootKeyData, which a normal Search never returns, take part in the comparison. The advisory calls this the trusted-request confusion. On its own, without operator control, it still only answers one exact-match question.

Combined, they give an ordered true or false test against a value you are not allowed to read. That is the primitive an oracle needs.

Turning Compare into an ordered oracle

The injection primitive is two short functions: 

def inject_ge(attribute: str) -> str:
    return attribute + ">"            # (attr=value) becomes (attr>=value)

def escape_ldap_filter_bytes(value: bytes) -> bytes:
    return b"".join(b"\\%02x" % b for b in value)

The operator change is the appended >. I send the attribute as msKds-RootKeyData>, and Samba formats (msKds-RootKeyData>=...).

The value needs more care, because the filter is built with %*s, a length-bounded copy of a C string. A raw value that contains a zero byte would truncate at the first NUL, and the server would compare a shortened value instead of the real candidate. I send every byte as a \XX hex escape. The escaped form has no NUL, so it survives the format string, and the LDB filter parser unescapes \XX back to the original byte before the match. The comparison then runs against the exact candidate I chose.

msKds-RootKeyData is an octet string, and its matching rule compares octet strings as raw bytes, with a shorter value sorting before a longer one that shares its prefix. So (attr>=candidate) answers whether the stored bytes are greater than or equal to the candidate in byte order. Each request returns compareTrue (result code 6) or compareFalse (result code 5). On a patched server the injected attribute name fails attribute-name validation and the request returns invalidAttributeSyntax (code 21) instead, which is how detection tells the two apart.

Recovering a value byte by byte

A greater-or-equal test recovers one byte at a time. 

def recover_byte(self, prefix: bytes) -> int:
    if not self.ge(prefix + b"\x01"):
        return 0x00
    lo, hi = 1, 0xFF
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if self.ge(prefix + bytes([mid])):
            lo = mid
        else:
            hi = mid - 1
    return lo

prefix is the bytes recovered so far, and ge(x) asks whether the stored value is at least prefix + x. The first probe asks for prefix + 0x01. If that is false, the next byte is 0x00 and it cost one request. Otherwise a binary search over 0x01 to 0xFF finds the largest byte value whose answer is still true. That search runs at most eight times, so a non-zero byte costs the first probe plus up to eight more, nine requests at most, and a zero byte costs one.

Deciding the next byte and deciding where the value ends are different questions. recover_byte assumes another byte exists. Whether to call it again depends on the length. msKds-RootKeyData is 64 bytes, so the loop simply stops at 64. When the length is unknown, the oracle probes prefix + 0x00 after each byte. Because a shorter stored value sorts before the same prefix followed by any further byte, a true answer there means at least one more byte remains, and a false answer means the value ends at the current prefix. That probe is the only place the zero-versus-end ambiguity is resolved.

The ceiling for the 64-byte key is nine requests per byte, so 576 requests, and the real total is lower whenever a byte is zero or its search settles in eight steps. The exact count depends on the key, so I do not quote a fixed number here; the tool reports it per run in its --json output and in the recover command.

The recovered bytes are exact under three conditions: the server answers each Compare consistently, the attribute really uses octet-string ordering, and the length is fixed and known. For msKds-RootKeyData all three hold, since it is a fixed 64-byte octet string. The derivation step then gives independent confirmation, because one wrong byte changes the derived NT hash completely, and the lab checks that hash against the controller.

Finding a root key you cannot read

The oracle needs a target DN, and the root key object is one an ordinary user cannot enumerate. KDS root keys live under CN=Master Root Keys,CN=Group Key Distribution Service,CN=Services in the configuration partition, as msKds-ProvRootKey objects. Samba hides those objects from normal users, so a one-level search of the container usually returns nothing, and list-keys says so when it finds none.

A gMSA account provides the way in. The account exposes msDS-ManagedPasswordID, which anyone who can read the account can read. KDSExtract parses that blob, whose envelope magic is KDSK, for the root key GUID and the key identifier (L0, L1, L2) the password was derived under, then builds the root key DN directly from the GUID: 

def kds_root_key_dn(ncs, guid):
    return f"CN={guid},CN=Master Root Keys," \
           f"CN=Group Key Distribution Service,CN=Services,{ncs.configuration}"

This is the path GoldenGMSA uses to locate the root key for a managed account. The read is what changes. GoldenGMSA reads msKds-RootKeyData with rights that allow it. Here the attribute is unreadable, so the Compare oracle recovers it instead. The oracle never issues a Search against the root key object, so it needs no read right on it, only the ability to send a Compare.

Deriving the password offline

Offline here is specific. The derivation touches no network, but it needs four inputs first, and three of them come from the directory: the root key bytes from the oracle, the root key GUID and the GKID from msDS-ManagedPasswordID, and the account SID from objectSid. Once those are collected, the password is a fixed computation.

MS-GKDI specifies that computation, and KDSExtract reimplements it with the standard library only. The primitive is SP 800-108 in counter mode with HMAC. Each block is keyed by the current key and fed a counter, a label, a context, and the output length in bits: 

msg = struct.pack(">I", i) + label + b"\x00" + context + struct.pack(">I", L)
out += hmac.new(key, msg, hash_name).digest()

The context is the GkdiDerivationContext: the root key GUID in little-endian byte order, then the three signed GKID indices, with a fixed gMSA security descriptor appended at the L1 stage. Serialization is load bearing. The GUID is the little-endian form, the indices are signed 32-bit, and the security descriptor bytes are part of the HMAC input. Any of these wrong produces a different key with no error.

Two labels drive the walk, both UTF-16LE and NUL terminated: "KDS service" for the seed keys and "GMSA PASSWORD" for the password. The seed is built in three levels. The L0 seed comes from the root key. The L1 seed starts at index 31 with the security descriptor in the context and walks down to the target L1 index. The L2 seed, when present, walks from index 31 down to the target L2 index. That structure is what lets a controller hand out keys bound to a time window without exposing the root key.

The last step applies the "GMSA PASSWORD" label with the account SID as context to produce 256 bytes, then runs the post-processing Windows uses: any UTF-16 code unit that is zero gets its low byte set to one. The NT hash is MD4 of those UTF-16LE bytes, so KDSExtract ships its own MD4 and keeps the runtime dependency free.

The hash algorithm is a property of the root key, stored in msKds-KDFParam. That attribute is itself confidential, so a normal user usually cannot read it. When it is readable the tool uses it. When it is not, the tool derives two candidates, SHA512 first because Samba uses it for keys it creates, then SHA256 because that is the Windows default. The derivation produces a candidate per hash. It does not know which one is right until something accepts it.

Computing a candidate is offline. Confirming it is the real password is not. The tool offers --verify-bind, which tries an LDAP simple bind as the gMSA with the derived password. As written, that check opens a fresh connection on the configured port, 389 by default, with no TLS and no fallback to LDAPS, unlike the main client, which retries on 636 when Samba refuses a cleartext bind. Against a default Samba that answers strongerAuthRequired to a cleartext simple bind, --verify-bind therefore reports failure for a correct password, because the transport was rejected rather than the password. The dependable confirmation in this project is the NT-hash comparison the lab performs. The client also does not validate TLS certificates, which fits the self-signed lab controllers and makes it unsafe on an untrusted network.

One more edge case shows up in the output. A small fraction of gMSA passwords contain unpaired UTF-16 surrogates, which cannot be represented as a valid simple-bind string. The tool reports that, still prints the raw password bytes and the NT hash, and the lab verifies those against the controller.

What the lab establishes

There are two levels of validation, and they prove different things.

The unit suite checks the GKDI math in isolation. It includes the twelve derivation vectors from Samba's own GkdiSelfTests, covering SHA1, SHA256, SHA384, and SHA512 and both the L1 and L2 seed cases, and the suite passes at commit 80a08cc. That confirms the derivation against a reference, independent of any network behavior.

The lab checks the full chain against a real controller. It builds two Samba controllers from upstream git tags, 4.24.4 and 4.24.5, provisions identical domains with a backdated KDS root key and a gMSA, then runs the tool against both. The assertions that matter are not the verdict text. The lab recovers each root key through the oracle and compares the bytes against the controller's own msKds-RootKeyData from samba-tool domain kds root-key list --show-secrets, and it derives each gMSA password and compares its NT hash against the controller's stored unicodePwd from samba-tool user getpassword. The script exits non-zero unless every recovered key and every derived hash matches. A passing run means the oracle reconstructed the controller's secret byte for byte and the offline derivation reproduced the password the controller would hand out.

What the run checks Samba 4.24.4 (vulnerable) Samba 4.24.5 (fixed)
Injected greater-or-equal compare Evaluates, oracle live Rejected, invalidAttributeSyntax (21)
Oracle recovery of msKds-RootKeyData Matches the controller's --show-secrets value Not reachable
Offline-derived gMSA NT hash Matches the stored unicodePwd Not reachable

The run also calls kdsextract check against each controller. That command sends an operator-injection probe against an ordinary attribute, and when it can find a gMSA-referenced root key, a second probe against the confidential attribute. On the vulnerable controller both evaluate; on the patched one the first returns invalidAttributeSyntax. check is a quick verdict, not the proof. Its one-line VULNERABLE string reads that confidential attributes participate even in the case where no gMSA-referenced root key was available to run the second probe, so on its own it can claim more than it tested. The per-probe detail is in the --json output. The result worth trusting is the byte-for-byte key match and the NT-hash match, which the lab enforces by exit code rather than by reading a verdict string.

Fixed versions and detection

The bug is fixed in Samba 4.24.5, 4.23.10, and 4.22.11. All AD DC releases from 4.0.0 are affected, and the gMSA path specifically needs 4.21.0 or later, where gMSA support exists. There is no configuration workaround. The fix validates the attribute name and escapes the value so the operator can no longer be injected, and marks the Compare internal search as untrusted so the confidential-attribute checks apply again.

For detection, the injection has a recognizable shape: a burst of Compare requests on one connection, attribute names ending in >, against objects under CN=Master Root Keys. On a patched controller those requests return invalidAttributeSyntax, which also distinguishes a patched controller from a vulnerable one.

Running it

The tool installs with its tests and has no runtime dependencies beyond the standard library. The README covers options and output in full; the common path is: 

pip install .
kdsextract check     --host dc --user lowpriv@lab.local
kdsextract dump-gmsa --host dc --user lowpriv@lab.local --name 'svcgmsa$'
kdsextract pwn       --host dc --user lowpriv@lab.local

check prints one of two verdicts, which are the exact strings the lab matches against: 

VULNERABLE (CVE-2026-58222): injected compare evaluates and confidential attributes participate
NOT VULNERABLE: attribute operator injection rejected (invalidAttributeSyntax 21) -- fixed Samba
